# Markdown文章SEO写作方法

Markdown 只是内容格式，搜索引擎最终分析的通常是网站生成的 HTML 页面。因此，SEO 写作的重点不是在文中加入更多关键词，而是让主题明确、结构清楚、信息完整，并确保发布系统能够输出可抓取的标题、正文、链接和元数据。

## 先确定搜索意图与文章边界

动笔前，先判断读者搜索这个主题时想解决什么问题。常见搜索意图包括：

- **了解概念**：例如“Markdown 是什么”
- **学习操作**：例如“Markdown 表格怎么写”
- **解决故障**：例如“GitHub Pages 图片不显示”
- **比较选择**：例如“Markdown 编辑器哪个好”
- **寻找模板**：例如“Markdown 博客文章模板”

一篇文章最好围绕一个主要意图展开。假设目标主题是“Markdown 图片添加方法”，正文应优先回答语法、相对路径、替代文本和常见错误，而不是花大量篇幅介绍 Markdown 的发展历史。

关键词可以自然拆分为三个层次：

1. **核心主题**：文章要解决的主要问题。
2. **相关问题**：用户完成任务时通常还会遇到的问题。
3. **必要术语**：准确解释内容所需的技术词汇。

可先列出简短提纲，再判断每个段落是否服务于主题。与搜索意图关系很弱的内容应删除或单独成文，避免页面看似丰富，实际却让读者难以快速找到答案。

## 设计标题与 Markdown 层级

页面标题应准确说明内容，不必刻意塞入多个近义词。较好的标题通常包含主题、任务或适用场景，例如：

- Markdown 表格写法与对齐方法
- GitHub Pages 中的 Markdown 图片路径配置
- Markdown 文章目录设计与标题层级规范

如果发布系统已经把文章标题渲染为页面的 `<h1>`，正文一般从 `##` 开始。二级标题负责划分主要步骤，三级标题用于解释某一步的细节。不要为了放大字体而跳级。

```markdown
## 添加本地图片

### 使用相对路径

### 检查发布后的文件位置

## 添加网络图片
```

这样的结构通常会生成连续的 `<h2>` 和 `<h3>`，有利于读者浏览，也便于搜索引擎理解段落关系。应避免下面几类问题：

- 多个章节使用含义近似的标题；
- 从二级标题直接跳到四级标题；
- 标题只有“介绍”“其他”“更多”等模糊词；
- 每一两句话就创建一个新标题；
- 用加粗文本代替真正的标题层级。

文章较长时可以添加目录，但目录应指向真实的标题锚点。不同 Markdown 渲染器生成锚点的规则可能不同，发布后需要实际点击检查。

## 写好开头、正文与问题答案

开头不必先讲宽泛背景，应尽快说明文章能解决什么问题、适用于什么环境，以及是否存在版本或平台差异。前两段最好让读者确认“这篇内容与我的问题有关”。

正文可以采用“结论—步骤—解释—示例”的组织方式：

1. 先给出可执行的方法；
2. 再解释为什么这样做；
3. 提供最小可用示例；
4. 补充限制条件和常见错误。

例如介绍链接语法时，不仅要给出代码，还应解释链接文字的写法：

```markdown
阅读 [GitHub Pages 官方文档](https://docs.github.com/pages)，了解支持的发布方式。
```

“点击这里”无法充分描述目标页面，而具体的链接文字可以帮助读者预判内容。与此同时，不要把同一个关键词机械放进每个标题、段落和链接中。术语重复应来自表达需要，而不是为了制造所谓的关键词密度。

教程中的示例还要能够执行。涉及命令、路径或配置时，应注明适用环境；如果不同工具的 Markdown 方言存在差异，例如表格、脚注或任务列表支持情况不同，也要明确提示读者以当前渲染器为准。

## 优化 description 与页面元信息

Description 应独立概括页面内容，让用户在搜索结果中判断页面是否值得访问。它不是标题的简单复述，也不需要罗列关键词。较实用的写法是包含“主题、解决范围、适用价值”：

> 介绍 Markdown 表格的基础语法、对齐设置与常见渲染问题，并提供可直接修改的示例。

建议保持自然完整。搜索引擎可能根据查询改写摘要，因此 description 只是重要参考，并不能保证按原文展示。

Markdown 文件中的标题和摘要如何进入 HTML，取决于 CMS、静态站点生成器或主题模板。发布后应查看网页源代码，确认最终页面包含合理的：

```html
<title>页面标题</title>
<meta name="description" content="页面摘要">
<link rel="canonical" href="https://example.com/article/">
```

Canonical 用于提示规范网址，但只有在存在重复 URL、参数网址或多种访问路径时才更具实际意义。不要把所有页面都错误地指向首页。若使用 GitHub Pages，页面通常由 Jekyll 或自定义构建流程生成；元数据、站点地图和 canonical 是否存在，取决于主题、布局及插件配置，并非创建 Markdown 文件后自动全部具备。

## 处理链接、图片与可读性

内部链接应连接真正相关的文章。例如，在“Markdown 图片语法”中链接到“相对路径说明”，比集中在文末堆放大量无关链接更有帮助。重要页面也不应成为没有任何站内入口的孤立页面。

图片应同时考虑路径、尺寸和替代文本：

```markdown
![Markdown 编辑器中的表格预览](../images/markdown-table-preview.png)
```

替代文本应描述图片展示的内容或作用，不要写成关键词列表。纯装饰图片可以使用空替代文本，但教程截图通常应说明关键界面。发布前还要压缩体积，并确认移动端不会横向溢出。

可读性方面，可以采用这些做法：

- 一个段落集中表达一个观点；
- 操作步骤使用有序列表；
- 并列信息使用无序列表或表格；
- 命令、文件名和参数使用行内代码；
- 长代码块注明语言，便于高亮；
- 重要限制直接写明，不用夸张的“绝对有效”。

表格适合比较固定字段，但在手机上可能较难阅读。内容较长时，列表往往比多列表格更稳妥。

## 发布前进行技术与内容检查

SEO 写作不能停留在 Markdown 源文件，最终应检查生成后的网页。可按下面的顺序核对：

- 页面是否能在未登录状态下正常访问；
- 标题是否唯一，且与正文主题一致；
- 页面是否只有一个主要一级标题；
- description 是否自然、完整；
- 标题层级是否连续；
- 内部链接和外部链接是否可用；
- 图片路径、替代文本和显示尺寸是否正确；
- 代码示例是否经过验证；
- 移动端是否容易阅读；
- 页面是否被错误设置为 `noindex`；
- robots.txt 是否误拦截必要页面资源；
- 站点地图是否包含应公开的规范网址。

内容发布后，还可以根据搜索查询、页面停留情况和读者反馈更新章节。若用户经常搜索某个文中尚未回答的问题，应补充具体答案；若文章涉及工具版本，则应在版本变化后复查示例。

高质量的 Markdown SEO 文章，本质上是把准确内容、清晰结构和可靠发布结果结合起来。语法规范能改善内容维护，页面元信息能帮助系统理解主题，而真正决定文章长期价值的，仍是它是否完整解决了读者的问题。
