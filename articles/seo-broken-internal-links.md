# 网站失效内链检测与修复指南

{% raw %}

## 什么是失效内链，为什么需要处理

内链是从网站一个页面指向同一网站其他资源的链接。常见失效情况不只有 404，还包括：

- **404 或 410**：目标页面不存在或已永久删除。
- **5xx 错误**：服务器或应用暂时无法返回页面。
- **错误重定向**：链接经过多次跳转、形成循环，或被转到无关页面。
- **软 404**：HTTP 状态码为 200，但页面实际显示“内容不存在”。
- **锚点失效**：页面可以打开，但 `#section-name` 对应的元素不存在。
- **资源链接错误**：图片、CSS、JavaScript 或下载文件无法访问。
- **环境相关错误**：链接在本地正常，上线后因路径、大小写或域名变化而失效。

失效内链会妨碍用户继续浏览，也会浪费搜索引擎抓取资源。大量错误链接还可能影响网站结构的可理解性。不过，修复内链不等于排名一定上升，应将其视为网站维护、用户体验和技术 SEO 的基础工作。

## 扫描前先确定检测范围

开始检测前，应明确哪些 URL 属于网站内部。除了主域名，还可能包括：

- `www.example.com` 与 `example.com`
- HTTP 与 HTTPS 版本
- 子域名，例如 `docs.example.com`
- 多语言目录，例如 `/zh/`、`/en/`
- CDN 或静态资源域名
- 测试环境、预览域名和历史域名

建议先准备站点的标准域名、XML Sitemap，以及是否允许访问测试环境等信息。扫描生产网站时要控制并发和请求频率，避免给服务器造成额外压力。

检测结果还应排除并单独处理以下链接：

- `mailto:`、`tel:`、`javascript:`
- 需要登录后才能访问的地址
- 带临时签名或短期令牌的下载链接
- 因防火墙、限流或反爬策略返回 403、429 的页面

看到非 200 状态码时不要直接判定页面已经失效。例如，扫描器请求被拦截也可能返回 403，需要使用浏览器或服务器日志再次确认。

## 使用工具批量检测失效内链

### 桌面爬虫扫描

Screaming Frog SEO Spider、Sitebulb 等爬虫可以从首页或 Sitemap 开始抓取。一般流程如下：

1. 输入网站首页并启动扫描。
2. 查看响应状态码为 4xx、5xx 的内部 URL。
3. 检查 3xx URL 是否存在多跳重定向。
4. 使用“Inlinks”或类似功能查看哪些页面包含错误链接。
5. 导出来源页面、目标 URL、锚文本和状态码。

扫描时不要只导出错误目标地址。真正用于修复的信息是“哪个页面中的哪一条链接指向了它”。

对于依赖 JavaScript 生成链接的网站，普通 HTML 抓取可能看不到完整内容。此时可启用渲染模式，但渲染扫描通常更慢，也更消耗服务器和本地资源。

### 命令行检测

希望在本地或持续集成流程中检查链接，可以使用 LinkChecker：

```bash
pip install linkchecker
linkchecker https://example.com --check-extern
```

只关注站内链接时，可以根据项目需求配置忽略规则。扫描大型网站前，建议先对测试环境或指定目录运行，确认不会访问注销链接、批量删除接口等危险地址。

浏览器开发者工具也适合检查单个页面：打开 Network 面板，刷新页面并按状态码筛选，即可发现加载失败的图片、脚本和接口请求。但它不适合替代全站爬虫。

### 搜索平台与服务器日志

Google Search Console 的页面索引报告可能显示部分“未找到（404）”URL，但它不是完整的内链检测器，也不会列出所有来源页面。服务器访问日志则能帮助确认搜索引擎或用户是否仍在请求旧地址。

较稳妥的做法是交叉使用：

- 爬虫：发现当前页面中的错误链接；
- Sitemap：检查计划提交给搜索引擎的 URL；
- 搜索平台：了解搜索引擎曾发现的问题；
- 日志：判断失效 URL 是否仍有实际访问。

## 按错误类型选择修复方式

### 目标页面仍然存在

如果页面只是更换了路径，应首先把站内链接直接改为新 URL，避免用户和爬虫经过不必要的跳转。然后在旧 URL 上设置 301 或 308 永久重定向，以承接书签、外链和历史访问。

例如：

```text
错误内链：/blog/old-guide
正确内链：/guides/new-guide
旧地址：301 重定向到 /guides/new-guide
```

不要把所有失效页面统一跳转到首页。目标不相关时，这种处理会让用户困惑，也可能被搜索引擎视为软 404。

### 页面已经永久删除

根据内容价值选择以下方式：

1. 有高度相关的替代页面：更新内链，并将旧地址重定向到替代页面。
2. 没有替代内容：删除或改写来源页面中的链接。
3. 页面明确永久下线：旧地址可返回 410；普通 404 也能表达不存在。
4. 页面未来会恢复：可暂时返回 503，并合理设置 `Retry-After`，不要长期保留。

如果被删除页面仍出现在 Sitemap 中，应同步移除。仅设置 canonical 标签不能修复 404，也不能替代重定向。

### 链接拼写或路径错误

重点检查：

- 路径大小写，例如 `/About/` 与 `/about/`
- 相对路径层级，例如 `../images/a.png`
- 多余或缺失的斜杠
- 文件扩展名变化
- URL 编码和中文字符
- HTTP、HTTPS 或端口写错
- 锚点名称与页面 `id` 不一致

修复时尽量使用网站统一的 URL 规范。对于内容管理系统，可优先使用页面选择器或内部资源 ID 生成链接，减少手工输入路径产生的错误。

## GitHub Pages 常见内链问题

GitHub Pages 部署后的路径规则可能与本地预览不同，尤其需要注意项目站点。用户或组织站点通常位于：

```text
https://username.github.io/
```

项目站点通常位于：

```text
https://username.github.io/repository/
```

如果项目站点中的链接写成 `/about/`，浏览器会访问域名根目录下的地址，而不是 `/repository/about/`。使用 Jekyll 时，可通过过滤器结合配置生成路径：

```liquid
<a href="{{ '/about/' | relative_url }}">关于</a>
```

同时在 `_config.yml` 中正确设置 `url` 和项目站点所需的 `baseurl`。不要手工重复拼接仓库名，否则可能产生双重路径。

GitHub Pages 运行在区分大小写的环境中。本地文件名为 `Guide.md`，链接却写成 `guide.html`，在部分本地系统中可能正常，上线后则会失败。修改文件名大小写时，Git 也可能没有立即识别，可显式执行：

```bash
git mv Guide.md temp.md
git mv temp.md guide.md
```

此外，Markdown 标题生成的锚点可能受渲染器和中文标点影响。不要凭感觉拼写锚点，应以上线后的实际 `id` 为准。

## 建立修复优先级并验证结果

面对大量错误时，可以按影响排序：

1. 导航栏、页脚和模板中的全站性错误；
2. 有自然流量或外部链接的页面；
3. 重要栏目页、产品页和转化页面；
4. Sitemap 中仍提交的失效 URL；
5. 普通文章中的单个错误链接；
6. 长期无人访问且没有引用的历史地址。

完成修改后重新抓取网站，确认：

- 来源页面已经指向正确目标；
- 新目标返回预期的 200 状态码；
- 旧地址的重定向不超过必要次数；
- 没有重定向循环；
- Sitemap、canonical 和导航链接使用最终 URL；
- 图片、脚本及页面锚点能够正常访问。

对于经常发布或迁移内容的网站，可在每次部署前检查新增和修改页面，并定期执行全站扫描。持续监控比集中清理更有效：它能在路径调整、模板改版或文件重命名后尽早发现问题，避免少量错误逐渐扩散到整个站点。
