# 百度蜘蛛抓取频率与主机负载关联分析

{% raw %}

## 抓取频率为什么会影响主机负载

百度蜘蛛访问页面时，服务器需要完成连接处理、路由匹配、文件读取或动态渲染。[抓取](./baidu-crawl-response-time.html)量增加是否会造成明显压力，主要取决于页面类型和系统架构。

对于纯静态页面，一次抓取通常只是读取文件并传输内容，CPU 消耗较低，压力更多体现在网络带宽和并发连接。对于 WordPress、论坛、商品搜索页等动态页面，每次请求可能触发 PHP、数据库查询、模板渲染及外部接口调用，少量抓取也可能放大 CPU 和数据库负载。

需要注意，抓取频率与负载之间不一定是单向因果关系：

- 百度蜘蛛请求增多，可能直接推高 CPU、I/O 或数据库连接数。
- 主机原本已经过载，响应速度下降，使请求长时间占用连接，看起来像蜘蛛造成了压力。
- 网站新增大量 URL、更新站点地图或改变内链结构后，蜘蛛集中发现页面，抓取量和负载同时上升。
- 伪装成 Baiduspider 的采集程序可能制造异常流量，不能只凭 User-Agent 判断。

因此，分析重点不是简单比较“访问量”和“CPU”，而是确认抓取时间、请求类型、响应耗时及资源指标是否同步变化。

## 同时采集蜘蛛日志与主机指标

首先从 Nginx 或 Apache 访问日志中提取疑似百度[蜘蛛](./baidu-crawl-status-code-analysis.html)请求。以常见的 Nginx 日志为例：

```bash
grep -i "Baiduspider" /var/log/nginx/access.log > /tmp/baidu.log
```

按分钟统计请求数量：

```bash
awk '{print $4}' /tmp/baidu.log \
  | cut -d: -f1,2,3 \
  | sort | uniq -c
```

实际日志格式可能不同，生产环境更适合使用 GoAccess、ELK、Loki 或[日志分析](./baidu-crawler-identification.html)脚本进行聚合。建议至少记录以下字段：

- 请求时间和来源 IP
- URL、请求方法与 User-Agent
- HTTP 状态码
- 响应时间
- 返回字节数
- 上游应用响应时间
- 缓存是否命中

同时采集同一时间粒度的主机数据：

- CPU 使用率与 Load Average
- 内存、Swap 使用量
- 磁盘 I/O 等待时间
- 网络流入、流出带宽
- Nginx 活跃连接数
- PHP-FPM、Java 或 Node.js 工作进程占用
- 数据库慢查询、连接数和查询吞吐量

可以通过 `top`、`vmstat`、`iostat`、`sar` 临时观察，也可以使用 Prometheus、Grafana、Zabbix 等工具保存历史趋势。例如：

```bash
vmstat 5
iostat -xz 5
sar -n DEV 5
```

只看某个时刻的 CPU 截图很难得出结论。抓取日志和监控指标应使用相同的时区，并尽量按一分钟或五分钟聚合。

## 如何判断二者是否真正相关

可以建立一张按时间排列的数据表，将每分钟的 Baiduspider 请求数与 CPU、I/O、响应时间等指标放在一起：

| 时间 | 蜘蛛请求数 | CPU | I/O Wait | 平均响应时间 |
|---|---:|---:|---:|---:|
| 10:00 | 18 | 25% | 2% | 180 ms |
| 10:01 | 96 | 72% | 14% | 850 ms |
| 10:02 | 110 | 86% | 20% | 1.4 s |

如果多个抓取高峰均伴随资源指标上升，并且高峰结束后负载恢复，说明二者可能存在较强关联。但还要进一步拆分 URL 类型和响应状态。

### 按页面类型拆分

同样是每分钟 100 次抓取，静态文章与站内搜索页的成本可能完全不同。可按路径分类：

- `/static/`、图片和 CSS：重点看带宽与磁盘读取。
- `/article/`：检查页面缓存和数据库查询。
- `/search/`、筛选参数页：检查复杂查询和重复 URL。
- `/api/`：检查接口计算量及外部依赖。
- 404 页面：检查是否触发动态模板、数据库查询或大量重定向。

### 检查响应时间和状态码

如果蜘蛛请求上升时出现大量 `499`、`502`、`503` 或 `504`，往往说明应用进程、反向代理或数据库已接近容量上限。大量 `301`、`302` 则可能意味着蜘蛛正在抓取旧 URL 或重定向链。

还应观察响应时间分布，而不是只看平均值。少数耗时十几秒的动态请求，可能持续占用工作进程，导致后续正常用户请求排队。

### 排除其他流量干扰

将同一时段的普通用户、其他搜索引擎和未知机器人分别统计。如果总请求量上涨，但 Baiduspider 占比很低，就不应把负载[问题](./baidu-crawl-error-analysis.html)归因于百度抓取。

User-Agent 可以伪造。对异常来源 IP，可进行反向 DNS 查询，再对得到的主机名做正向解析，确认是否回到原 IP；具体识别规则应以百度官方公开说明为准。不要仅根据名称中出现“Baiduspider”就加入白名单。

## 常见高负载场景及判断方法

### 动态页面没有缓存

表现为抓取次数不算高，但 PHP-FPM、数据库 CPU 和慢查询明显增加。可以使用应用性能监控或慢查询日志，确认每个被抓取页面执行了多少 SQL，以及是否存在重复查询。

### 参数 URL 数量失控

排序、筛选、分页和跟踪参数可能组合出大量近似 URL，例如：

```text
/list?sort=price&page=2
/list?page=2&sort=price
/list?page=2&utm_source=test
```

蜘蛛持续发现这些地址，会增加抓取消耗。应统一参数顺序，移除无业务价值的跟踪参数，并通过规范链接、内链治理和必要的 robots 规则减少无效入口。robots.txt 只能控制是否允许抓取，不能替代 URL 规范化，也不保证已发现的 URL 从搜索结果中消失。

### 大文件或图片消耗带宽

此时 CPU 可能不高，但出口带宽接近上限，用户访问仍会变慢。应检查返回字节数、图片尺寸、压缩方式及 CDN 命中情况。

### 错误页面形成循环

错误的日历链接、无限分页、重定向循环或软 404，会让蜘蛛反复访问低价值地址。需要结合日志中的高频 URL、状态码和跳转链定位源头，而不是直接封禁整个蜘蛛。

## 降低抓取压力的处理顺序

优先优化单次请求成本，再考虑控制请求数量。直接屏蔽百度蜘蛛可能影响页面发现和内容更新，不适合作为常规解决方案。

1. **启用页面缓存**：对更新频率较低的文章页使用全页缓存，减少应用和数据库执行。
2. **增加静态资源缓存**：正确设置 `Cache-Control`、文件指纹，并视业务情况使用 CDN。
3. **治理重复 URL**：修复无限分页、无意义参数、错误内链和重定向链。
4. **优化慢查询**：添加合适索引，避免抓取页面触发全表扫描或高成本统计。
5. **返回正确状态码**：不存在的内容应返回真正的 `404` 或 `410`，服务器临时过载可返回 `503`，但不要长期维持。
6. **设置分级限流**：优先针对高成本路径、异常 IP 或整体并发设置保护，避免只根据 User-Agent 粗暴限流。
7. **检查百度搜索资源平台数据**：结合抓取诊断、抓取异常等可用信息判断搜索引擎看到的响应情况；平台具体功能可能随站点权限和版本变化。

`Crawl-delay` 不是 robots.txt 的通用标准指令，各搜索引擎支持情况不同，不宜把它作为控制百度抓取速度的唯一方案。限流也应保留合理余量，否则大量 `429` 或 `503` 可能降低抓取效率。

## 建立可持续的监控基线

完成优化后，应继续记录一到两周数据，比较抓取请求数、缓存命中率、服务器响应时间和用户侧可用性。理想结果不一定是抓取次数下降，而是相同或更高的抓取量下，CPU、I/O 和数据库开销保持稳定。

建议设置分层告警，例如 CPU 持续高于阈值、I/O Wait 异常、应用队列堆积、蜘蛛请求错误率上升。每次发布新模板、调整站点地图或批量生成页面后，也应重点观察日志变化。

判断百度蜘蛛是否导致主机负载，关键在于把访问日志与系统指标按时间对齐，并进一步定位高成本 URL。通过缓存、URL 治理、数据库优化和合理的容量保护，通常比简单封禁抓取更稳妥，也更有利于维持正常的页面发现与服务器可用性。
