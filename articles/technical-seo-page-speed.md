# 网站页面速度技术SEO优化方法

{% raw %}

页面速度优化不能只盯着某一次 Lighthouse 得分。真正有效的技术 SEO 工作，应先识别真实用户遇到的瓶颈，再分别处理服务器响应、关键资源加载、交互延迟和布局稳定性，同时避免因懒加载或脚本渲染影响搜索引擎获取正文。

## 先建立可重复的速度测量基线

建议同时使用实验室数据和真实用户数据：

- **PageSpeed Insights**：同时展示 Lighthouse 测试和 Chrome UX Report（CrUX）真实用户数据。
- **Google Search Console**：通过“核心网页指标”报告查看同类 URL 的整体问题。
- **Chrome DevTools**：使用 Network、Performance、Coverage 面板定位慢请求、长任务和未使用代码。
- **WebPageTest**：适合测试不同地区、设备和网络条件下的加载过程。

核心网页指标应重点观察：

- **LCP**：最大内容绘制，良好标准为不超过 2.5 秒。
- **INP**：交互到下一次绘制，良好标准为不超过 200 毫秒。
- **CLS**：累积布局偏移，良好标准为不超过 0.1。

这些标准通常按真实访问数据的第 75 百分位评估。CrUX 使用过去约 28 天的数据，因此代码上线后，现场数据不会立刻变化。

测试时应记录页面类型、设备、网络环境和测试日期。首页、文章页、商品页、分类页使用的模板不同，不能只测试首页后推断全站表现。

## 降低服务器响应和传输成本

HTML 返回过慢会推迟后续资源发现。先检查首字节时间，并区分问题来自应用程序、数据库、第三方接口还是网络距离。

常见处理方法包括：

1. 为公开页面增加页面缓存或静态化输出。
2. 优化慢查询，避免一次请求执行大量重复数据库查询。
3. 使用 CDN 缓存图片、CSS、JavaScript 和字体。
4. 开启 Brotli 或 Gzip 压缩文本资源。
5. 使用 HTTP/2 或 HTTP/3，减少大量资源并发传输的额外成本。
6. 为带版本号的静态文件设置长期缓存。

例如，Nginx 可为指纹化静态资源设置缓存：

```nginx
location ~* \.(css|js|png|jpg|jpeg|webp|avif|svg|woff2)$ {
    expires 1y;
    add_header Cache-Control "public, max-age=31536000, immutable";
}
```

只有文件名会随内容变化时才适合使用 `immutable`，例如 `app.a81c3f.js`。若固定文件名长期缓存，更新后用户可能继续获得旧文件。

不要把所有 HTML 都设置为长期公共缓存。登录状态、购物车和个性化页面需要按业务逻辑配置，否则可能造成数据串用。

## 优先优化 LCP 关键内容

LCP 元素通常是首屏主图、横幅、标题区域或大段文本。可在 DevTools Performance 面板中确认具体元素，再沿着其加载链路排查。

如果 LCP 是图片，应：

- 输出接近实际显示尺寸的图片，避免下载超大原图。
- 优先采用 AVIF 或 WebP，并保留兼容格式。
- 使用 `srcset` 和 `sizes` 提供响应式图片。
- 不要对首屏 LCP 图片使用 `loading="lazy"`。
- 必要时使用 `fetchpriority="high"` 提高其请求优先级。

```html
<img
  src="/images/hero-1280.webp"
  srcset="/images/hero-640.webp 640w,
          /images/hero-1280.webp 1280w"
  sizes="100vw"
  width="1280"
  height="720"
  fetchpriority="high"
  alt="页面速度分析界面">
```

关键 CSS 应尽早加载。体积很小的首屏样式可以内联，其余样式延后处理，但不要为了追求分数而造成无样式内容闪烁。

`preload` 只应用于确定会立即使用的关键资源：

```html
<link rel="preload"
      href="/fonts/site.woff2"
      as="font"
      type="font/woff2"
      crossorigin>
```

过量预加载会与真正重要的资源争夺带宽，反而可能拖慢 LCP。

## 减少 JavaScript 对 INP 的影响

INP 较差通常意味着主线程被长时间占用。常见来源包括大型框架包、第三方统计脚本、广告、在线客服和一次执行过多工作的事件处理器。

可按以下顺序处理：

- 删除未使用的依赖和重复引入的库。
- 按路由或功能拆分 JavaScript，仅在需要时加载。
- 对非关键脚本使用 `defer`，独立且不依赖顺序的脚本可考虑 `async`。
- 将超过 50 毫秒的长任务拆成多个小任务。
- 对输入、滚动和窗口变化事件进行防抖或节流。
- 将复杂计算移至 Web Worker，减少主线程阻塞。
- 延迟加载非必要的第三方组件。

```html
<script src="/js/site.js" defer></script>
```

不能只看 JavaScript 文件大小。一个压缩后较小但执行复杂的脚本，也可能产生较长的解析和执行时间。应结合 Performance 面板中的 Long Task、事件处理时间和主线程调用栈判断。

对于依赖客户端渲染的页面，还要确认正文和内部链接能够被搜索引擎正常渲染。重要内容优先使用服务端渲染或静态生成，不要要求用户点击、滚动后才把正文写入 DOM。

## 控制图片、字体与布局偏移

CLS 常见于未预留空间的图片、广告、嵌入组件，以及网页字体替换后文字尺寸变化。

图片和视频应声明 `width`、`height`，或通过 CSS 的 `aspect-ratio` 预留比例：

```css
.article-cover {
  width: 100%;
  aspect-ratio: 16 / 9;
  object-fit: cover;
}
```

首屏以下图片可以使用原生懒加载：

```html
<img src="/images/example.webp"
     width="800"
     height="450"
     loading="lazy"
     alt="优化后的网页图片">
```

懒加载实现不能依赖滚动后才生成真实图片地址，也不应把重要内容只放在 CSS 背景图中。图片链接应直接存在于可渲染的 HTML 属性中，并提供准确的替代文本。

字体方面，优先使用 WOFF2，删除不需要的字重和字符集。可通过 `font-display: swap` 减少文字长期不可见，但要选择指标接近的后备字体，避免替换时发生明显位移。

页面顶部不要在加载后突然插入公告栏、广告或 Cookie 提示。确需展示时，应提前预留空间，或使用不推动主体内容的合适布局。

## 上线后验证真实效果

每次优化最好只调整一组可识别的因素，并保留前后数据。上线后需要检查：

1. 页面是否返回正常的 HTTP 状态码。
2. CSS、JavaScript、图片和字体是否出现 404 或跨域错误。
3. 移动端正文、链接和结构化数据是否仍可访问。
4. CDN 与浏览器缓存是否命中。
5. 不同地区和低速网络下是否仍有改善。
6. Search Console 的核心网页指标是否在后续周期逐步变化。

速度提升通常有利于用户体验，也能降低服务器和传输压力；对于页面量很大的网站，稳定的响应能力还有助于搜索引擎更高效地访问页面。但性能只是搜索系统考虑的众多因素之一，不能保证排名或收录。

合理的执行顺序是：先修复服务器和 LCP 瓶颈，再减少主线程阻塞，随后处理 CLS 和非关键资源，最后建立持续监控。这样比一次性安装多个“加速插件”更容易定位收益，也能避免缓存冲突、脚本失效和内容不可见等副作用。
