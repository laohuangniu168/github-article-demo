# 网站搜索引擎可抓取性优化指南

{% raw %}

## 先区分抓取、索引与排名

“可抓取”是指搜索引擎爬虫能够发现并访问网页，但这不等于网页一定会被索引，更不代表会获得较高排名。优化前应先区分三个环节：

1. **发现**：爬虫通过站内链接、外部链接或站点地图找到 URL。
2. **抓取**：服务器允许访问，并返回可处理的内容和状态码。
3. **索引**：搜索引擎判断页面是否适合进入索引库。

如果页面没有任何可跟踪链接，即使内容质量不错，也可能长期无法被发现；如果 `robots.txt` 阻止抓取，搜索引擎便难以读取页面中的正文、canonical 或 `noindex`；即使抓取正常，重复、低价值或内容不足的页面仍可能不被索引。

因此，可抓取性优化的目标是减少技术障碍，让重要页面容易被发现、稳定访问，并向搜索引擎传递一致的索引信号。

## 检查 URL、状态码与服务器响应

重要页面应当使用稳定、唯一且可长期访问的 URL，并返回符合实际情况的 HTTP 状态码。

- 正常页面返回 `200 OK`
- 永久迁移使用 `301` 或 `308`
- 临时迁移可使用 `302` 或 `307`
- 已删除且无替代内容时返回 `404` 或 `410`
- 避免频繁出现 `500`、`502`、`503` 等服务器错误
- 不要让错误页面显示“内容不存在”却仍返回 200，这属于软 404

重定向应尽量一步完成。例如，旧地址不要先跳转到 HTTP 版本，再跳到带 `www` 的地址，最后才到新页面。过长的重定向链会增加抓取成本，也更容易因中间节点故障而中断。

还要检查服务器是否误拦截爬虫。常见问题包括防火墙规则过严、CDN 挑战页面、访问频率限制不合理，以及把正常爬虫请求统一返回 `403` 或 `429`。不能只依据容易伪造的 User-Agent 放行访问；如需验证搜索引擎爬虫，应采用对应搜索引擎公布的 DNS 验证方法。

对于大型网站，可以分析服务器日志中的爬虫访问记录，重点关注：

- 哪些目录被频繁抓取
- 重要页面是否长期没有请求
- 5xx、404 和重定向请求的比例
- 参数 URL 是否消耗大量抓取资源
- 页面响应时间是否存在明显波动

## 正确配置 robots 与索引指令

`robots.txt` 必须位于站点根目录，例如：

```text
https://www.example.com/robots.txt
```

一个基础配置可以是：

```txt
User-agent: *
Disallow: /admin/
Disallow: /internal-search/

Sitemap: https://www.example.com/sitemap.xml
```

不要直接写成：

```txt
User-agent: *
Disallow: /
```

这会阻止匹配该规则的爬虫抓取整个网站。上线前还应检查测试环境中的全站屏蔽规则是否被带到正式环境。

需要注意，`robots.txt` 控制的是**抓取权限**，并不是可靠的删除索引工具。某个 URL 即使被禁止抓取，仍可能因为外部链接等原因以仅显示地址的形式出现在搜索结果中。

如果希望搜索引擎读取页面后不将其编入索引，可以在允许抓取的前提下使用：

```html
<meta name="robots" content="noindex, follow">
```

非 HTML 文件可通过 HTTP 响应头发送：

```http
X-Robots-Tag: noindex
```

不要同时禁止抓取并设置 `noindex`，因为爬虫无法访问页面时，通常也无法看到其中的 `noindex` 指令。修改规则后，还要考虑搜索引擎重新抓取需要时间，结果不会立即变化。

## 用内部链接建立清晰的发现路径

搜索引擎主要依靠链接发现页面。首页、栏目页、专题页与内容页之间应形成可理解的层级，而不是依赖站内搜索框或用户手动输入 URL。

推荐采用普通 HTML 链接：

```html
<a href="/guides/crawlability/">抓取优化指南</a>
```

不要只用没有 `href` 的点击事件跳转：

```html
<span onclick="openPage()">查看内容</span>
```

虽然部分搜索引擎可以执行 JavaScript，但标准链接的识别更稳定，也方便浏览器、辅助工具和其他爬虫使用。

内部链接优化应重点处理以下问题：

- 确保重要页面距离首页不需要过多点击
- 给链接使用能说明目标内容的锚文本
- 修复失效链接和错误重定向
- 为孤立页面补充来自栏目页或相关文章的入口
- 分页列表提供可抓取的下一页、上一页或页码链接
- 不要让无限滚动成为访问后续内容的唯一方式

面包屑导航也有助于表达页面层级，但它不能替代完整的栏目结构。对商品、文章或文档数量较多的网站，还应定期检查是否有页面只存在于 XML 站点地图中，却没有任何站内链接指向。

## 提交站点地图并控制重复 URL

XML 站点地图适合帮助搜索引擎发现新增、更新较深或内部链接较少的页面。文件中的地址应使用完整 URL：

```xml
<url>
  <loc>https://www.example.com/guides/crawlability/</loc>
  <lastmod>2025-03-01</lastmod>
</url>
```

站点地图应只包含希望被抓取和索引的规范页面，避免放入以下地址：

- 返回 404 或 5xx 的页面
- 被 `noindex` 标记的页面
- 被 `robots.txt` 阻止的页面
- 重定向 URL
- 指向其他 canonical 地址的重复页面

`lastmod` 应反映实际内容更新时间，不要每天自动改写所有页面日期。站点地图可以在搜索引擎站长平台提交，也可以在 `robots.txt` 中声明，但提交并不意味着其中所有 URL 都会被收录。

筛选、排序、跟踪参数和打印版本容易生成大量重复页面。例如：

```text
/products?sort=price
/products?sort=new
/products?utm_source=newsletter
```

应根据业务需要统一内部链接形式，并在重复页面中指定首选地址：

```html
<link rel="canonical" href="https://www.example.com/products/">
```

canonical 是规范化提示，并非绝对指令。若页面内容、内部链接、站点地图和 canonical 相互矛盾，搜索引擎可能选择其他规范 URL。分页页面如果内容不同，通常应保留各自可访问的 URL，并避免全部错误地 canonical 到第一页。

## 处理 JavaScript 内容并持续验证

依赖客户端 JavaScript 加载正文的网站，可能出现初始 HTML 几乎为空、接口请求失败或渲染时间过长的问题。部分搜索引擎能够执行 JavaScript，但能力、频率和等待时间并不一致。

对标题、正文、商品信息和导航等核心内容，优先考虑：

- 服务端渲染
- 静态生成
- 预渲染后输出完整 HTML
- 在无 JavaScript 或脚本失败时保留基本内容与链接

GitHub Pages 会发布静态文件，并可结合 Jekyll 生成 HTML，适合直接输出可抓取内容；它不会自动替网站完成 canonical、站点地图或 robots 配置，这些仍需由主题、插件或构建流程正确生成。

完成调整后，可使用搜索引擎站长工具的 URL 检查功能查看抓取状态、已选 canonical 和渲染结果，同时结合浏览器开发者工具、命令行与日志验证。例如：

```bash
curl -I https://www.example.com/page/
curl -A "Googlebot" -I https://www.example.com/page/
```

最终检查重点应包括：重要 URL 能否通过链接发现，是否返回正确状态码，robots 与索引指令是否冲突，页面主要内容能否在 HTML 或渲染结果中读取，以及站点地图是否只提交规范页面。把这些基础条件保持一致，能够降低无效抓取和技术误判的概率，为后续内容评估与索引建立更可靠的环境。
