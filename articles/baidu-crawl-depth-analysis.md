# 百度蜘蛛抓取深度分析实战方法

{% raw %}

## 先明确“抓取深度”到底指什么

分析百度蜘蛛抓取深度时，不能只看 URL 中有几层目录。实际工作中常见三种“深度”：

1. **URL 目录深度**：例如 `/seo/log/analysis/` 看起来有三层，但目录层级不等于蜘蛛需要点击三次。
2. **站内点击深度**：从首页或栏目入口出发，到目标页面最少需要经过多少个可抓取链接。
3. **日志访问深度**：不同点击深度的页面，在服务器日志中获得了多少次百度蜘蛛请求。

其中最有分析价值的是后两项。一个 URL 即使结构很长，只要首页直接链接它，点击深度仍然是 1；反过来，一个短 URL 如果只能通过多次分页找到，实际深度可能很高。

建议先约定统一口径：

- 深度 0：首页或指定种子页；
- 深度 1：首页直接链接的页面；
- 深度 2：至少经过两次链接才能到达；
- 无深度：站内链接图中无法从种子页到达的孤立 URL。

日志本身通常不能完整还原蜘蛛的访问路径，因为搜索引擎请求不一定携带可靠的 Referer。因此，实战中应先计算站内点击深度，再与百度蜘蛛日志关联。

## 获取并验证百度蜘蛛访问日志

Nginx 或 Apache 的访问日志至少需要包含以下字段：

- 请求时间；
- 客户端 IP；
- Host 和请求 URL；
- HTTP 状态码；
- User-Agent；
- 响应字节数；
- 响应时间。

Nginx 可以使用类似格式：

```nginx
log_format seo '$remote_addr [$time_local] "$request" '
               '$status $body_bytes_sent "$http_referer" '
               '"$http_user_agent" $request_time';

access_log /var/log/nginx/access.log seo;
```

修改配置后需要检查并重新加载，且新格式只对之后产生的日志生效。

初筛时可以查找包含 `Baiduspider` 的 User-Agent：

```bash
grep -i "Baiduspider" /var/log/nginx/access.log > baidu-candidate.log
```

但 User-Agent 很容易伪造，不能据此认定请求来自百度。对于候选 IP，应进行反向 DNS 查询，再对得到的主机名做正向解析，确认解析结果包含原 IP。不要长期依赖网上流传的固定 IP 段，因为搜索引擎的网络范围可能变化。

基本验证流程如下：

```bash
host 220.181.xxx.xxx
host reverse-result.example
```

批量分析时可以缓存验证结果，避免对同一 IP 反复查询。若日志前面还有 CDN 或反向代理，还要确认记录的是访客真实 IP，而不是代理节点 IP。

## 建立页面深度表并关联日志

点击深度可以通过站点爬虫、内部链接导出工具或自建程序计算。计算时应从首页、主要栏目页等种子 URL 开始，对 HTML 中可访问的内部链接执行广度优先遍历。

简化逻辑如下：

```python
from collections import deque

depth = {homepage: 0}
queue = deque([homepage])

while queue:
    current = queue.popleft()

    for target in extract_internal_links(current):
        target = normalize_url(target)

        if target not in depth:
            depth[target] = depth[current] + 1
            queue.append(target)
```

这里有几个容易影响结果的细节：

- 统一 HTTP 与 HTTPS、大小写及末尾斜杠规则；
- 去除广告追踪参数和无意义查询参数；
- 正确处理 301、302 与 canonical；
- 区分真正的 HTML 链接和依赖交互触发的链接；
- 不把 robots.txt 禁止抓取的页面当作正常中转节点；
- 分页、筛选页应按网站真实策略决定是否进入链接图。

完成后生成页面表，例如：

| URL | 点击深度 | 页面类型 | 可索引状态 |
|---|---:|---|---|
| `/` | 0 | 首页 | 是 |
| `/seo/` | 1 | 栏目页 | 是 |
| `/seo/log-guide.html` | 2 | 内容页 | 是 |
| `/old/page.html` | 无 | 孤立页 | 否 |

随后将规范化后的日志 URL 与页面表关联，按天、页面类型和深度统计请求次数。URL 规范化必须与深度计算阶段使用同一套规则，否则参数、斜杠和重定向会造成大量匹配失败。

## 用指标判断深层页面是否抓取不足

只看蜘蛛请求总量意义有限。建议至少观察以下指标：

### 各深度抓取覆盖率

```text
抓取覆盖率 = 周期内被百度蜘蛛请求过的页面数 ÷ 该深度有效页面总数
```

例如深度 2 有 800 个有效页面，其中 520 个在 14 天内被请求过，覆盖率为 65%。不同规模、更新频率的网站不能直接比较，应重点观察本站趋势。

### 抓取次数分布

统计各深度的总请求次数、独立 URL 数和单 URL 平均请求次数。如果大量请求集中在深层参数页，而重要内容页长期没有访问，可能存在抓取资源分配不合理。

### 状态码与响应时间

按深度统计 200、3xx、404、5xx 比例。需要重点排查：

- 蜘蛛反复请求已经失效的 404 URL；
- 多段重定向链；
- 深层页面 5xx 比例明显偏高；
- 某类页面响应时间持续较长；
- 同一内容因参数产生大量重复地址。

还应按页面类型拆分。商品详情、文章、标签页和站内搜索页的价值不同，将它们混在一起容易得出错误结论。

## 从异常分布定位具体结构问题

常见问题可以通过“深度表＋日志”交叉识别：

1. **深度较高且长期未抓取**
   检查页面是否只存在于多层分页、年份归档或筛选组合中，并确认入口链接能够在返回的 HTML 中被发现。

2. **深度不高但没有抓取记录**
   可能受到 robots.txt、状态码、错误 canonical、链接拼写或服务器访问限制影响，也可能只是观察周期过短。

3. **参数 URL 抓取量过大**
   检查排序、筛选、跟踪参数是否不断生成新组合。可通过链接生成规则、参数清理、重定向或 canonical 减少重复，但不能把 canonical 当作禁止抓取指令。

4. **孤立页面出现在日志中**
   说明百度可能从历史链接、外部链接或 Sitemap 发现了页面。若页面仍有价值，应补充正常的站内入口；若已废弃，则返回符合实际情况的状态码。

5. **深层页面频繁返回 5xx**
   这通常是技术稳定性问题，应先检查数据库查询、缓存命中和应用超时，而不是急于调整链接结构。

## 优化后如何做对照验证

改动应尽量小批量实施，便于判断原因。可以先选择一个栏目进行以下调整：

- 从相关栏目页或专题页增加真实、有语义的内部链接；
- 缩短重要内容到主要入口的最短点击距离；
- 修复断链、循环重定向和错误规范地址；
- 合并无价值的参数组合；
- 更新 XML Sitemap，准确反映希望被发现的规范 URL；
- 保证重要链接使用可解析的 `<a href="...">` 形式。

Sitemap 有助于搜索引擎发现 URL，但不能替代清晰的站内链接结构，也不代表提交后一定会抓取或收录。

验证时应使用相同长度的前后周期，例如各取 14 天，并排除发布量、服务器故障和活动流量差异。重点比较：

- 深度 3 以上有效页面的抓取覆盖率；
- 重要页面首次被请求的时间；
- 参数页、404 和重定向请求占比；
- 各页面类型的抓取频率；
- 百度搜索资源平台中可获得的抓取与索引反馈。

抓取增加不等于收录，收录也不等于排名提升。更可靠的目标是让重要页面更容易被发现、减少无效请求，并确保蜘蛛访问时获得稳定、规范且有价值的内容。持续保留深度表、原始日志和改动日期，才能把一次排查变成可重复的技术 SEO 监测流程。
