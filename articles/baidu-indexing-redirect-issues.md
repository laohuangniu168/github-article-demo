# 重定向问题导致百度收录异常的排查方法

{% raw %}

网站改版、启用 HTTPS、更换域名后，如果百度长期收录旧地址、新地址迟迟不进入索引，或者搜索结果中的 URL 反复变化，通常需要先检查重定向是否正确。排查重点不是“有没有跳转”，而是百度蜘蛛能否通过稳定、简短且语义明确的跳转，到达可正常抓取的最终页面。

## 先判断异常是否真的由重定向引起

常见的重定向相关表现包括：

- 旧 URL 仍被收录，新 URL 很少出现；
- 百度搜索结果中的 HTTP、HTTPS、带 `www` 和不带 `www` 版本混杂；
- 页面在浏览器中可以打开，但抓取工具提示跳转次数过多；
- 同一个 URL 有时返回 301，有时返回 302；
- 百度蜘蛛访问时被跳转到首页、验证页或错误页；
- 改版后索引量明显波动，服务器日志中出现大量旧地址抓取；
- 最终页面返回 200，但中间经过多次域名或协议跳转。

需要注意，收录变化也可能来自内容质量、抓取频率、站点稳定性、robots 限制或页面重复，并非所有异常都是重定向造成的。因此应先随机抽取几类 URL：

1. 已收录的旧地址；
2. 希望收录的新地址；
3. 搜索结果中版本不一致的地址；
4. 百度搜索资源平台中提示抓取异常的地址；
5. 服务器日志里被 Baiduspider 高频访问的地址。

每类检查若干页面，不要只测试首页。首页跳转正常，并不代表文章页、分页、参数页和静态资源都配置正确。

## 检查状态码与完整跳转链

可以使用 `curl` 查看响应头：

```bash
curl -I http://example.com/article/123
```

重点关注状态码和 `Location`：

```text
HTTP/1.1 301 Moved Permanently
Location: https://www.example.com/article/123
```

继续查看完整跳转过程：

```bash
curl -IL http://example.com/article/123
```

理想情况通常是一次跳转后到达返回 `200 OK` 的目标页面：

```text
http://example.com/article/123
  -> 301 https://www.example.com/article/123
  -> 200
```

如果出现下面这种链路，就应考虑简化：

```text
http://example.com/a
  -> https://example.com/a
  -> https://www.example.com/a
  -> https://www.example.com/a/
  -> 200
```

多级跳转会增加抓取成本，也更容易因为其中某一环配置失效而中断。应尽量让所有非规范版本直接跳到最终 URL，而不是依次完成 HTTP、主机名和尾斜杠转换。

还要区分常见状态码：

- **301**：通常用于长期迁移，例如 HTTP 转 HTTPS、旧域名转新域名、永久更换 URL；
- **302**：表示临时跳转，适合短期活动或临时维护，不宜长期承担永久改版迁移；
- **307、308**：分别具有临时和永久语义，并保留请求方法；使用前要确认服务器、代理和业务端兼容；
- **200**：最终可访问页面应正常返回 200，而不是展示错误内容的“软 404”。

不要仅通过浏览器地址栏判断。浏览器会缓存 301，还可能受插件、HSTS 或本地 DNS 影响，命令行和服务器日志更适合定位真实响应。

## 排除循环跳转、错误落地和规则冲突

重定向循环常由多层配置互相冲突引起。例如 Nginx 强制 HTTPS，CDN 回源却使用 HTTP，而源站又根据请求协议继续跳转，最终形成循环。

Nginx 中可以将 HTTP 直接跳到唯一规范地址：

```nginx
server {
    listen 80;
    server_name example.com www.example.com;
    return 301 https://www.example.com$request_uri;
}
```

HTTPS 站点则只保留一个规范主机名：

```nginx
server {
    listen 443 ssl;
    server_name example.com;
    return 301 https://www.example.com$request_uri;
}
```

排查时应逐层确认：

- CDN 或云代理是否启用了额外的 HTTPS 跳转；
- 源站是否正确识别 `X-Forwarded-Proto`；
- CMS 插件是否再次修改域名、协议或尾斜杠；
- 旧规则和新规则是否同时生效；
- 重定向是否保留原始路径与必要参数；
- 不存在的旧页面是否全部跳到首页。

将大量无对应关系的旧页面统一跳到首页并不理想。更合理的方式是跳到内容对应的新页面；确实没有替代内容时，可以返回 404 或 410，并在站内移除相关链接。

## 检查百度蜘蛛获得的响应是否不同

有些网站对普通浏览器返回正常页面，却对爬虫触发防火墙、地区判断、验证码或登录跳转。可以模拟百度蜘蛛查看响应：

```bash
curl -IL \
  -A "Mozilla/5.0 (compatible; Baiduspider/2.0; +http://www.baidu.com/search/spider.html)" \
  https://www.example.com/article/123
```

再与普通 User-Agent 的结果比较：

```bash
curl -IL \
  -A "Mozilla/5.0" \
  https://www.example.com/article/123
```

如果两者状态码、`Location` 或最终内容明显不同，应检查 CDN 防护、WAF、反爬策略和应用层代码。仅凭 User-Agent 无法证明访问者是真实 Baiduspider，分析服务器日志时还需要结合来源 IP 的反向解析和正向验证，避免把伪造爬虫当成百度抓取。

同时确认最终落地页没有被以下因素阻止：

- `robots.txt` 禁止抓取；
- 页面包含不符合预期的 `noindex`；
- canonical 指向另一个 URL；
- 页面必须执行 JavaScript 才能完成跳转；
- 登录、Cookie 或地区识别导致不同落地页；
- 返回 200，但正文是“页面不存在”或空白模板。

用于迁移的跳转应由服务器返回 HTTP 状态码完成，不建议依赖 JavaScript 或延时 Meta Refresh。

## 统一规范 URL，并处理 GitHub Pages 场景

站点应先确定唯一版本，例如：

```text
https://www.example.com/path/
```

然后统一处理 HTTP、HTTPS、主域名、`www`、大小写、尾斜杠和默认首页等变体。站内链接、站点地图、canonical 与重定向目标也应保持一致，避免一边声明 URL A 为规范页，一边又把 A 跳到 URL B。

如果使用 GitHub Pages，需要注意它不提供 Nginx、Apache 或 `.htaccess` 级别的自定义服务器规则，也不适合实现复杂的任意路径重定向。应在仓库设置中正确配置 Custom domain，并按 GitHub 文档配置 DNS 与 HTTPS。复杂的旧域名迁移或批量路径映射，通常要借助可配置重定向的 CDN、反向代理或独立服务器完成。

不建议仅创建一个包含 JavaScript 跳转的静态 HTML 页面来代替 301。浏览器虽然可能跳转成功，但搜索引擎获得的响应仍是 200，迁移信号不如服务器端永久重定向清晰。

## 修复后如何验证和持续观察

修改配置后，先清除 CDN 缓存，再批量验证不同类型的 URL：

```bash
curl -s -o /dev/null -w \
'%{url_effective} %{http_code} %{num_redirects}\n' \
-L http://example.com/article/123
```

确认最终地址、状态码和跳转次数符合预期。随后可以在百度搜索资源平台中使用抓取诊断等工具检查重要页面，并提交规范的新 URL 或站点地图。若属于站点改版，应根据实际情况使用平台提供的改版相关能力，而不是反复提交同一批地址。

服务器日志也应持续观察至少一个完整抓取周期，重点查看：

- Baiduspider 是否仍大量访问错误跳转；
- 301 后的目标页是否稳定返回 200；
- 是否存在 5xx、循环或超时；
- 新旧 URL 的抓取比例是否逐步变化；
- 站点地图中的 URL 是否与最终落地地址一致。

重定向修复不会让索引立即更新，也不能保证页面一定被收录。更可靠的做法是保持跳转长期稳定、减少链路、统一站内信号，并确保最终页面具备可抓取、可索引且有实际价值的内容。
