# 百度蜘蛛服务器日志分析完整指南

{% raw %}

## 分析前先确认日志是否完整

服务器日志能回答“百度蜘蛛访问了什么”，但不能直接证明页面已经收录或获得排名。分析前应确认日志至少包含以下字段：

- 客户端 IP
- 请求时间与时区
- Host、请求方法和 URI
- HTTP 状态码
- User-Agent
- 响应字节数
- 请求处理时间

Nginx 可使用类似配置：

```nginx
log_format seo '$remote_addr [$time_local] "$request" $status '
               '$body_bytes_sent $request_time '
               '"$http_referer" "$http_user_agent" host="$host"';

access_log /var/log/nginx/access.log seo;
```

修改后先用 `nginx -t` 检查配置，再平滑加载。Apache 的 Combined Log Format 已包含多数基础字段，但若要分析响应速度，需要额外记录请求耗时。

网站使用 CDN 或反向代理时，源站日志可能只记录节点 IP，且缓存命中的请求未必到达源站。此时应优先使用 CDN 提供的访问日志，并按照服务商文档配置可信代理 IP。不要直接信任任意请求携带的 `X-Forwarded-For`，否则攻击者可以伪造来源。

## 识别真正的百度蜘蛛

只搜索 `Baiduspider` User-Agent 并不可靠，因为任何客户端都能伪造该标识。正确方法是结合 User-Agent 和 IP 的双向 DNS 校验。

先从日志中找到一个待验证 IP：

```bash
grep 'Baiduspider' /var/log/nginx/access.log | head
```

对该 IP 进行反向解析：

```bash
dig -x 目标IP +short
```

然后对返回的主机名执行正向解析：

```bash
dig 返回的主机名 A +short
dig 返回的主机名 AAAA +short
```

应同时满足：

1. 反向解析得到的主机名符合百度搜索资源平台当前公布的蜘蛛 DNS 规则；
2. 将该主机名正向解析后，结果中包含原始访问 IP。

只检查主机名中是否出现“baidu”并不安全，例如恶意域名可能刻意包含相关字符串。IP 段和蜘蛛规则也可能变化，不建议长期维护一份来源不明的静态 IP 白名单。

实际工作中可以先按 User-Agent 汇总，再对高频 IP、异常请求 IP 和准备加入防火墙白名单的 IP 进行 DNS 校验，从而控制查询成本。

## 提取和清洗蜘蛛访问记录

对于当天的普通日志，可直接筛选：

```bash
grep 'Baiduspider' /var/log/nginx/access.log > baidu.log
```

同时处理轮转后的压缩日志：

```bash
{
  grep -h 'Baiduspider' /var/log/nginx/access.log*
  zgrep -h 'Baiduspider' /var/log/nginx/access.log*.gz
} 2>/dev/null > baidu-all.log
```

如果使用标准 Combined Log Format，请求 URI 通常位于第 7 列，状态码位于第 9 列。统计状态码：

```bash
awk '{count[$9]++} END {
  for (code in count) print code, count[code]
}' baidu-all.log | sort
```

查看抓取次数最多的 URL：

```bash
awk '{print $7}' baidu-all.log |
sort | uniq -c | sort -nr | head -30
```

如果只关注路径、不区分查询参数：

```bash
awk '{print $7}' baidu-all.log |
sed 's/?[^ ]*$//' |
sort | uniq -c | sort -nr | head -30
```

是否移除参数应根据分析目标决定。分页、筛选和追踪参数往往正是重复抓取问题的来源，过早删除会掩盖异常。

此外，应分别统计不同 Host、HTTP 与 HTTPS、带不带 `www` 的请求。多个站点混写到同一日志时，如果忽略 Host，可能把不同网站的同名路径合并。

## 重点观察哪些指标

单纯记录“蜘蛛来了多少次”价值有限，更重要的是判断抓取是否集中在正确页面。

### 状态码分布

- **200**：成功返回内容，但仍需判断是否为软 404 或重复页面。
- **301、308**：永久跳转，少量正常；大量连续跳转会浪费请求。
- **302、307**：临时跳转，应确认是否符合实际业务语义。
- **304**：缓存验证生效，通常不代表异常。
- **404、410**：页面不存在。410 明确表示资源已移除，但不应为了“清理收录”随意批量使用。
- **403、429**：可能被安全策略、限速规则或防火墙拦截。
- **5xx**：服务器、网关或程序错误，应优先排查。

### URL 类型与目录分布

将 URL 按内容目录、参数页、静态资源、接口和站内搜索页分类，观察蜘蛛请求是否集中在：

- 核心文章和产品页面；
- 无限制分页或筛选组合；
- Session ID、追踪参数等动态 URL；
- 已删除但仍被内链引用的地址；
- CSS、JavaScript、图片等渲染所需资源；
- 后台、测试环境或无价值的站内搜索结果。

不要看到蜘蛛抓取静态资源就一律禁止。搜索引擎可能需要 CSS 和 JavaScript 理解页面布局或渲染内容。

### 时间、IP 与响应性能

按小时或天统计请求量，可发现突然归零、异常暴增以及固定时段大量超时等问题。结合经过验证的蜘蛛 IP，还可以区分正常抓取与伪造 User-Agent 的扫描行为。

如果日志记录了 `$request_time`，应比较百度蜘蛛请求的平均值和高分位耗时。平均值容易掩盖少量极慢请求，因此更值得关注 P95、P99，以及慢请求对应的 URL 模板。

## 从异常现象定位技术问题

发现大量 3xx 时，先检查是否存在跳转链：

```text
http://example.com/a
→ https://example.com/a
→ https://www.example.com/a
→ https://www.example.com/new-a
```

应在业务允许时尽量让旧地址直接跳转到最终地址，并同步更新站内链接和 Sitemap。

大量 404 需要区分来源：如果旧 URL 仍有外链或可替代内容，可跳转至最相关的新页面；如果资源确实永久消失，返回真实的 404 或 410 即可，不要把所有失效页面都跳到首页。

参数 URL 被反复抓取时，可依次检查：

1. 模板是否生成了大量可点击参数链接；
2. 参数页面是否返回相同或高度相似内容；
3. canonical 是否指向合理的规范地址；
4. Sitemap 中是否只提交规范 URL；
5. 是否需要通过参数规则、链接结构或 robots.txt 控制抓取。

`robots.txt` 会限制抓取，但不能替代 URL 规范化，也不等同于删除搜索结果。已经被禁止抓取的页面，搜索引擎可能无法读取其 canonical、状态码或页面级指令，因此调整前应评估影响。

## 建立可持续的分析流程

建议按天生成一份报表，至少包含：

- 已验证蜘蛛 IP 和请求量；
- 总请求数、唯一 URL 数；
- 2xx、3xx、4xx、5xx 占比；
- 抓取最多的目录、参数和页面；
- 新出现的 404、403、429、5xx URL；
- 平均响应时间及 P95；
- 与前一天、前一周的变化。

日志保留周期应覆盖网站更新和搜索引擎重新抓取的过程，同时做好压缩、脱敏和访问权限控制。分析结果还应与百度搜索资源平台中的抓取、索引、Sitemap 等数据交叉验证：日志表示服务器收到过请求，平台数据则从另一个角度反映搜索引擎处理情况，两者不能互相替代。

有效的日志分析最终应落到具体问题上，例如修复错误状态码、缩短跳转链、减少无限参数组合、恢复被误拦截的资源或改善慢页面。持续比较调整前后的抓取结构和错误比例，才能判断技术处理是否真正生效，而不是只追求蜘蛛访问次数的增长。
