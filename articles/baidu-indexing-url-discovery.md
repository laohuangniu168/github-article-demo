# 提高百度发现新URL效率的方法

{% raw %}

百度发现新 URL，通常要经历“找到链接—发起抓取—解析内容—判断是否建立索引”几个环节。提交链接只能增加发现机会，不能代替内容质量判断，也不代表页面一定会被收录。实际优化应同时解决入口不足、抓取受阻和页面信号混乱等问题。

## 先确认新 URL 是否具备抓取条件

在增加提交渠道前，应先检查页面本身。否则，即使百度已经发现 URL，也可能因为技术问题无法正常抓取。

重点检查以下项目：

- URL 在未登录状态下可以访问；
- 返回真实的 HTTP `200` 状态码，而不是软 404；
- 没有被 `robots.txt` 禁止；
- 页面不存在 `noindex` 等阻止索引的指令；
- canonical 指向当前页面或正确的规范 URL；
- 没有多次跳转、循环跳转或设备端错误跳转；
- HTML 中能直接获得主要正文和链接；
- 页面加载速度及服务器稳定性处于可接受范围。

例如，下面的配置会阻止百度抓取 `/draft/` 目录：

```txt
User-agent: Baiduspider
Disallow: /draft/
```

修改 `robots.txt` 后，还要检查页面级别的 robots 设置，例如：

```html
<meta name="robots" content="noindex, nofollow">
```

如果页面需要公开收录，就不应保留上述 `noindex` 指令。对于主要内容依赖 JavaScript 异步渲染的网站，建议采用服务端渲染、静态生成或预渲染，让初始 HTML 包含标题、正文和关键链接，减少搜索引擎解析失败的可能。

## 用稳定的站内链接建立发现入口

搜索引擎最自然的 URL 发现方式仍然是跟踪已有页面中的链接。新内容如果只存在于数据库、站内搜索结果或必须点击按钮后才能出现，抓取程序很难及时找到。

发布页面后，可以从以下位置添加可抓取的链接：

1. 对应栏目页或分类页；
2. 首页的最新内容区域；
3. 相关文章、专题页或聚合页；
4. 按时间排列的文章归档页；
5. HTML 网站地图。

链接应使用标准的 `<a href="">` 形式：

```html
<a href="https://www.example.com/guide/new-page">新页面标题</a>
```

不要只依赖 JavaScript 点击事件、表单提交或无限滚动。无限滚动页面最好同时提供分页 URL，并确保分页之间存在普通超链接。

站内链接还应避免形成“孤儿页面”。一般来说，新页面距离首页或重要栏目页的点击层级越深，被发现的速度越容易受到影响。不过，也不必把所有新链接都堆到首页，应优先建设清晰、符合用户浏览逻辑的信息架构。

## 生成并持续更新 XML Sitemap

XML Sitemap 适合批量告知搜索引擎站内有哪些规范 URL，尤其适用于更新频繁、页面数量较多或内部链接层级较深的网站。

基础格式如下：

```xml
<?xml version="1.0" encoding="UTF-8"?>
<urlset xmlns="http://www.sitemaps.org/schemas/sitemap/0.9">
  <url>
    <loc>https://www.example.com/article/a</loc>
    <lastmod>2025-03-08</lastmod>
  </url>
  <url>
    <loc>https://www.example.com/article/b</loc>
    <lastmod>2025-03-07</lastmod>
  </url>
</urlset>
```

制作 Sitemap 时应注意：

- 只放置可公开访问、返回 `200` 的规范 URL；
- 不要加入登录页、搜索结果页、404 页面和被 robots 屏蔽的地址；
- `<lastmod>` 应反映页面内容的真实修改时间，不能每天批量伪造更新；
- URL 较多时，可拆分为多个 Sitemap，并使用 Sitemap 索引文件管理；
- 新页面发布或旧页面删除后，及时同步更新文件。

生成后，应在百度搜索资源平台中提交 Sitemap。具体入口和权限可能随平台调整，应以当前后台显示为准。Sitemap 的作用是提供 URL 清单，不等于强制抓取，也不能弥补页面质量或访问稳定性问题。

## 使用百度搜索资源平台主动提交

完成站点验证后，可以在百度搜索资源平台查看当前可用的链接提交方式。常见方式包括手动提交、Sitemap 以及普通收录 API；部分能力可能需要站点满足特定条件，并非所有网站都能使用。

如果后台提供普通收录 API，可以按官方生成的接口地址提交新增 URL。典型请求形式如下：

```bash
curl -H 'Content-Type:text/plain' \
  --data-binary @urls.txt \
  'https://data.zz.baidu.com/urls?site=https://www.example.com&token=你的令牌'
```

`urls.txt` 每行放置一个完整地址：

```txt
https://www.example.com/article/a
https://www.example.com/article/b
```

实际使用时需要注意：

- `site` 必须与平台中验证的站点一致，包括协议和域名；
- 接口令牌属于敏感信息，不应写入公开仓库或前端代码；
- 只提交新发布或发生实质更新的有效页面；
- 根据接口返回结果处理失败、额度不足或格式错误；
- 不要反复提交同一批 URL，频繁提交不会替代正常抓取。

对于静态网站，可以在构建完成后提取本次新增页面，再由部署脚本调用接口。GitHub Pages 本身不提供服务器端运行环境，但可以通过外部 CI 流程执行提交任务。若使用 GitHub Actions，应将令牌保存在 Secrets 中，避免直接写入工作流文件，同时确认站点在目标网络环境中的访问稳定性。

## 减少抓取过程中的服务器与 URL 障碍

百度已经获得 URL 后，服务器是否稳定会直接影响抓取。应重点排查以下问题：

- Baiduspider 请求频繁返回 `403`、`429` 或 `5xx`；
- CDN、防火墙或安全插件误拦截搜索引擎；
- TLS 证书错误或 HTTPS 配置不完整；
- 页面响应时间过长；
- 同一内容生成大量参数 URL；
- HTTP、HTTPS以及带 `www`、不带 `www` 的版本信号不统一。

不要仅凭 User-Agent 就永久放行访问者，因为该字段可以伪造。如需判断请求是否来自真实 Baiduspider，可结合百度官方说明进行反向 DNS 查询，并再做正向解析验证。

对于重复 URL，应通过统一内部链接、规范标签和必要的 `301` 跳转集中信号。例如网站确定使用 HTTPS 后，应将 HTTP 地址永久重定向到对应的 HTTPS 页面，而不是让多个版本同时返回相同内容。

## 通过日志和平台数据定位瓶颈

提高发现效率不能只看搜索结果中有没有 `site:` 页面。该查询结果不适合用作精确收录统计，更有效的方法是结合服务器日志与搜索资源平台数据判断问题发生在哪一步。

可以在访问日志中筛选 Baiduspider 请求：

```bash
grep -i "Baiduspider" access.log
```

然后观察：

- 新 URL 首次被请求的时间；
- 抓取返回的状态码；
- 百度是否持续访问 Sitemap；
- 哪些目录长期没有抓取记录；
- 是否存在大量无价值参数页消耗抓取资源。

如果 URL 已提交但长期没有抓取记录，应优先检查入口、robots、站点验证和服务器访问情况；如果已有抓取记录却迟迟没有进入索引，则更应检查内容独特性、页面完整度、重复内容和网站整体质量，而不是继续重复提交。

有效的做法是形成固定发布流程：页面上线后验证状态码与 canonical，加入栏目和相关推荐，更新 Sitemap，再提交本次新增 URL，最后通过日志确认抓取情况。把“可访问、可发现、可解析、值得索引”四个环节同时做好，通常比单纯增加提交次数更有意义。
