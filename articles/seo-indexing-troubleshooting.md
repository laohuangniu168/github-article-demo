# 网站搜索引擎收录问题排查指南

{% raw %}

网站页面迟迟搜不到，不一定意味着被搜索引擎处罚。一个页面进入搜索结果，通常要经历“被发现—允许抓取—成功解析—判断是否索引”几个阶段。排查时应先确定问题发生在哪一环，而不是反复提交网址或修改关键词。

## 先确认是未收录，还是排名较低

“搜索不到”可能有三种情况：

- 页面尚未进入索引库；
- 页面已收录，但目标关键词排名靠后；
- 搜索引擎选择了其他网址作为规范版本。

可以先使用 `site:` 命令做粗略检查：

```text
site:example.com
site:example.com/page-url
```

但 `site:` 结果并不完整，不能作为唯一判断标准。更可靠的方法是使用对应站长平台：

- Google：Search Console 的“网址检查”和“网页索引”报告；
- Bing：Bing Webmaster Tools 的 URL Inspection；
- 百度：百度搜索资源平台的索引量、抓取诊断等工具。

检查单个网址时，重点记录以下信息：

1. 搜索引擎是否知道该网址；
2. 最近一次抓取时间及抓取结果；
3. 是否允许编入索引；
4. 搜索引擎认定的规范网址；
5. 页面是否因重定向、重复或软 404 被排除。

如果全站页面都未收录，应优先检查域名、服务器、robots.txt 和站点级 `noindex`。如果只有部分栏目或新页面有问题，则更可能与内部链接、模板设置、内容重复或页面质量有关。

## 检查搜索引擎能否发现页面

搜索引擎首先需要获得网址。一个没有内部链接、没有站点地图、也没有外部入口的孤立页面，通常较难被及时发现。

### 检查内部链接

从首页或相关栏目出发，确认可以通过普通 HTML 链接到达目标页面：

```html
<a href="/guides/indexing.html">收录排查教程</a>
```

不要只依靠站内搜索框、表单提交或点击后才由 JavaScript 临时生成的入口。重要页面应出现在清晰的分类、导航、面包屑或相关文章中，并避免过深的点击层级。

同时检查链接是否写错，例如：

- 相对路径指向错误目录；
- HTTP 与 HTTPS 混用；
- `www` 与非 `www` 版本并存；
- URL 大小写不一致；
- 链接最终跳转到 404 页面。

### 检查 XML 站点地图

站点地图应列出希望被索引的规范网址，并返回 `200 OK`。示例：

```xml
<url>
  <loc>https://example.com/guides/indexing.html</loc>
  <lastmod>2025-03-01</lastmod>
</url>
```

不要把 404、重定向、`noindex` 或非规范网址放入站点地图。提交 Sitemap 有助于搜索引擎发现页面，但不代表页面一定会被收录。

## 排除抓取与服务器故障

使用命令行查看页面的实际响应：

```bash
curl -I -L https://example.com/page-url
```

理想情况下，最终网址应返回 `200`。常见异常包括：

- `404`：页面不存在或发布路径错误；
- `403`：服务器、防火墙或 CDN 拒绝访问；
- `429`：请求频率限制过严；
- `5xx`：服务器程序、网关或托管服务故障；
- 多次重定向：协议、域名或路径规则冲突；
- 软 404：状态码是 200，但正文实际显示“内容不存在”。

接着检查根目录下的 `robots.txt`：

```text
User-agent: *
Disallow: /private/
```

如果出现 `Disallow: /`，通常会阻止整个站点被抓取。还要留意是否误封了文章目录、CSS、JavaScript 或渲染页面所需的接口。

`robots.txt` 用于控制抓取，不是可靠的删除索引工具。若希望已收录页面退出搜索结果，应让搜索引擎能够访问页面并读取 `noindex`，或根据具体情况返回 `404`、`410`。如果一边禁止抓取，一边添加 `noindex`，爬虫可能无法看到该指令。

## 核对 noindex、canonical 与重定向

在页面源代码中查找 robots 指令：

```html
<meta name="robots" content="noindex,follow">
```

也要检查 HTTP 响应头是否存在：

```text
X-Robots-Tag: noindex
```

测试环境迁移到正式环境后，模板、SEO 插件或服务器配置残留 `noindex`，是整站不收录的常见原因。

然后检查规范链接：

```html
<link rel="canonical" href="https://example.com/page-url">
```

canonical 应指向当前页面的首选公开版本。如果多个页面都错误地指向首页，搜索引擎可能把这些页面视为重复版本。需要注意，canonical 是规范化信号，不是强制命令；站内链接、站点地图和重定向最好与其保持一致。

对于永久更换的网址，应使用服务器端 `301` 或 `308` 重定向，并尽量一次到达最终页面。不要让旧网址在多个协议、域名和路径之间循环跳转。

## 判断内容是否值得单独建立索引

页面技术上可抓取，不代表一定会被纳入索引。搜索引擎可能暂不索引以下页面：

- 正文很少，主要是导航、广告或模板内容；
- 大量页面只有城市名、产品名等少量字段不同；
- 标签页、筛选页和参数页重复度很高；
- 内容已被其他页面完整覆盖；
- 页面标题与正文不匹配；
- JavaScript 执行前几乎没有有效内容；
- 页面显示登录墙、空白状态或加载错误。

排查 JavaScript 页面时，可以对比“查看源代码”和浏览器开发者工具中的最终 DOM，并使用站长平台的实时测试或渲染截图。如果核心正文只能在复杂交互后出现，应考虑服务端渲染、静态生成或预渲染，而不是假设所有爬虫都能稳定执行前端逻辑。

内容优化的重点是回答真实问题：提供明确主题、完整信息、可验证细节和合理结构。合并高度重复的页面，删除无实际价值的批量页，通常比为每个页面机械增加字数更有效。

## 修复、提交与持续观察

建议按照影响范围和确定性排序处理：

1. 修复 5xx、403、404、错误重定向等访问问题；
2. 移除误设的 `noindex` 和 robots.txt 封锁；
3. 统一 HTTPS、主域名、canonical 与内部链接；
4. 更新站点地图并重新提交；
5. 加强重要页面的内部链接；
6. 改善重复、空白或渲染失败的内容；
7. 在站长平台申请重新抓取，并观察数天至数周。

GitHub Pages 站点还应确认仓库或发布源能够正常生成页面，目标文件确实位于发布分支或配置目录中。使用 Jekyll 时，以下划线开头的特殊目录、草稿和未来日期文章可能不会按预期发布；设置 `baseurl` 的项目站点也容易产生错误链接。自定义域名需同时检查 DNS、HTTPS 和跳转后的最终网址。GitHub Pages 可以托管 `robots.txt`、Sitemap 和静态页面，但提交后同样不能保证收录。

不要在短时间内反复提交同一网址。更有价值的做法是记录每次修复的日期、响应状态、抓取结果和索引变化。只要页面能够被稳定发现、正常抓取、正确声明规范版本，并提供独立价值，就具备进入索引的基础；至于是否收录以及何时展示，仍由搜索引擎综合判断。
