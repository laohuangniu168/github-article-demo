# 网站404页面SEO优化实战指南

{% raw %}

## 先判断哪些 URL 应该返回 404

404 表示服务器能够访问，但请求的资源不存在。对 SEO 而言，重点不是“消灭所有 404”，而是让不同类型的失效 URL 得到正确处理。

可以按以下规则判断：

| URL 情况 | 建议处理 |
|---|---|
| 用户输错地址、随机探测 URL | 返回 404 |
| 页面已永久删除，且没有替代内容 | 返回 404 或 410 |
| 页面更换了地址，内容仍然存在 | 301 重定向到新地址 |
| 多个旧页面合并成一个新专题 | 301 到相关的新专题页 |
| 商品暂时缺货，之后还会上架 | 保留 200，并说明缺货状态 |
| URL 因大小写、参数或格式变化产生重复 | 统一链接规则，必要时重定向 |

不要为了减少 404 数量，把所有失效地址都跳转到首页。搜索引擎可能将这种做法识别为软 404，而且用户也无法知道原内容去了哪里。

如果旧页面确实没有可替代内容，正常返回 404 并不是 SEO 故障。真正需要处理的是：站内仍在持续链接这些地址，或者本应重定向的页面错误地返回了 404。

## 确保服务器返回真实的 404 状态码

页面看起来像“内容不存在”，并不代表 HTTP 状态码正确。常见错误是页面显示“抱歉，未找到”，但服务器仍返回 `200 OK`。这类页面会被称为软 404，可能造成无效 URL 被反复抓取。

可以使用以下命令检查：

```bash
curl -I https://example.com/this-page-does-not-exist
```

正确结果应包含：

```text
HTTP/2 404
```

如果响应为 `200`、`301` 或 `302`，需要继续检查服务器、CMS、CDN和缓存规则。

### Nginx 配置示例

```nginx
error_page 404 /404.html;

location = /404.html {
    internal;
}
```

这里不要写成把所有错误地址 `301` 到 `/404.html`。`error_page 404 /404.html` 可以在展示自定义页面的同时保留原请求的 404 状态，而地址栏仍显示用户访问的错误 URL。

### Apache 配置示例

在 `.htaccess` 或虚拟主机配置中加入：

```apache
ErrorDocument 404 /404.html
```

同时确认 `/404.html` 文件确实存在，且错误处理没有被 CMS 路由或重写规则覆盖。修改后应分别测试普通错误地址、带参数地址和多层目录地址。

## 设计真正有帮助的自定义页面

404 页面不需要堆放关键词，它的主要任务是帮助访问者重新找到内容。一个实用的页面通常包括：

- 明确说明当前页面不存在、已移动或地址可能输入有误；
- 返回首页的入口；
- 站内搜索框；
- 主要栏目或热门内容链接；
- 与网站一致的导航、品牌和视觉样式；
- 必要时提供问题反馈方式。

提示文字可以直接、具体，例如：

> 没有找到你访问的页面。它可能已被删除或更换地址，你可以搜索相关内容，或者从下方栏目继续浏览。

避免只展示“404”三个数字，也不要在错误页面加载自动播放视频、大量推荐组件或体积过大的脚本。404 流量中可能包含爬虫、错误外链和地址探测，页面越复杂，服务器和前端资源消耗越高。

页面中的推荐链接应指向稳定、相关的真实页面，不能为了“传递权重”塞入几十个无关链接。导航链接也要定期检查，防止 404 页面本身继续链接到其他失效地址。

## 修复站内链接与错误重定向

自定义页面只能改善体验，不能代替链接修复。站内出现大量可点击的 404，会影响用户浏览，也会让搜索引擎重复抓取无效路径。

建议按以下顺序处理：

1. **抓取全站链接**
   使用网站爬虫、CMS 链接检查工具或日志分析，找出哪些页面链接到了失效 URL。

2. **区分链接来源**
   优先检查主导航、面包屑、正文、相关推荐、图片地址、分页和 XML Sitemap。

3. **直接更新内部链接**
   如果新地址已知，应把页面中的旧链接改为新链接，而不是长期依赖多次重定向。

4. **为有替代内容的旧 URL 配置 301**
   重定向目标必须与原页面主题相关。不要把所有已删除文章统一跳到栏目首页。

5. **清理重定向链**
   避免出现“旧地址 A → 旧地址 B → 新地址 C”，应尽量让 A 直接跳到 C。

6. **移出 Sitemap**
   XML Sitemap 应主要提交规范、可索引且返回 200 的页面。已删除并返回 404 的 URL 不应长期保留其中。

外部网站指向错误 URL 时，如果能确认该地址原本对应某个现有页面，可以设置相关的 301；如果只是拼写错误、垃圾链接或随机扫描请求，通常无需逐条处理。

## GitHub Pages 的 404 页面配置

GitHub Pages 支持自定义 404 页面，但它是静态托管环境，不能像 Nginx 一样编写服务器级重定向规则。

在发布源的根目录创建：

```text
404.html
```

如果项目使用 Jekyll，也可以创建 `404.md`，并通过布局生成页面，例如：

```markdown
---
layout: default
permalink: /404.html
---

页面不存在，请返回首页或查看文章目录。
```

这里的 Front Matter 是 GitHub Pages 项目文件示例，不是本文的页面元数据。发布后，应访问一个确定不存在的地址进行验证：

```bash
curl -I https://username.github.io/project/not-found-test
```

如果使用项目站点、第三方主题、自定义构建目录或 GitHub Actions 部署，需要确认最终发布产物的根目录中确实包含 `404.html`。仅把文件放在源码仓库某个未发布目录里不会生效。

GitHub Pages 不提供可自由配置的服务器端 301 规则。若要迁移页面，可以在旧 HTML 中使用跳转提示或客户端跳转，但这与服务器返回的 301 并不等价。涉及大规模 URL 迁移时，更适合使用支持重定向规则的托管平台、CDN或反向代理。

## 监控效果并避免反复出现

上线后不要只检查 404 页的视觉效果，还要持续观察错误来源。可结合以下数据：

- Google Search Console 中的网页索引和抓取信息；
- Bing Webmaster Tools；
- Web 服务器或 CDN 访问日志；
- 网站爬虫报告；
- 分析工具中的 404 页面访问记录。

在自定义页面中记录原始请求路径时，应避免收集不必要的个人信息。可以按访问次数统计 404 URL，再优先处理高频地址。高频错误通常来自旧版页面迁移、导航模板错误、外部链接、静态资源路径变更或 URL 大小写不一致。

完成配置后，至少检查四项：不存在的 URL 返回 404、有效页面返回 200、迁移页面正确返回 301、Sitemap 不再提交失效地址。404 本身不会自动伤害网站，问题通常来自错误状态码、无关跳转和未修复的内部链接。让状态码表达真实情况，并为用户提供清晰的下一步，才是长期可维护的处理方式。
