# 百度网站收录异常诊断完整指南

{% raw %}

百度收录异常通常表现为新页面长期不出现、索引量突然下降、旧链接仍被展示，或搜索结果中的标题和摘要不符合预期。诊断时不要只看 `site:` 查询，而应区分“能否发现、能否抓取、是否进入索引、是否值得保留”四个环节，再逐项验证。

## 先确认属于哪一种收录异常

不同现象对应的排查方向并不相同，建议先记录异常开始时间、影响目录和页面数量。

- **新站或新页面不收录**：优先检查链接发现、服务器可访问性、robots 规则和页面质量。
- **索引量突然下降**：重点回顾近期改版、URL 变更、模板调整、服务器故障和批量删除操作。
- **只有部分目录不收录**：通常与目录级 robots 规则、内链不足、重复内容或模板配置有关。
- **收录后又消失**：可能是页面价值不足、内容重复、长期返回异常状态码，或被错误设置为不可索引。
- **旧 URL 仍在搜索结果中**：需要检查旧地址是否正确跳转、是否仍被内链和 Sitemap 引用。
- **标题、摘要异常**：不等于页面未收录。搜索引擎可能根据查询词和页面内容重写展示信息。

`site:example.com` 适合快速抽样，但结果数量不是精确索引量，也不能作为唯一判断依据。更可靠的参考是百度搜索资源平台中的索引量趋势、抓取情况，以及具体 URL 的实际搜索表现。

## 检查百度能否发现并抓取页面

页面必须先被发现，才可能进入后续处理。孤立页面即使内容完整，也可能长期没有抓取机会。

首先检查目标页面是否能从首页、栏目页或相关文章中通过普通 `<a href="">` 链接到达。不要只依赖站内搜索框、表单提交或 JavaScript 点击事件。重要页面应形成清晰的内链路径，并避免距离首页层级过深。

然后检查百度搜索资源平台中的相关数据：

1. 查看抓取频次是否明显下降。
2. 使用抓取诊断确认百度蜘蛛访问时得到的响应。
3. 查看是否存在 DNS、连接超时、服务器错误等记录。
4. 对新增或重要链接使用平台提供的链接提交方式；提交只用于帮助发现，不代表一定收录。

可在本地检查 HTTP 响应：

```bash
curl -I https://example.com/page/
curl -L -I https://example.com/old-page/
```

正常内容页通常应直接返回 `200`。需要重点处理的情况包括：

- `5xx`：服务器或上游服务故障；
- `403`：防火墙、CDN 或安全规则拒绝访问；
- `404`：页面不存在；
- 重定向链过长或循环；
- HTTP 与 HTTPS、带 `www` 与不带 `www` 之间跳转不一致；
- 页面显示“内容不存在”，却返回 `200`，形成软 404。

不要仅用修改 User-Agent 的方式断言百度一定能访问。真实抓取还受来源 IP、DNS、网络线路和安全策略影响，应结合平台抓取诊断与服务器日志判断。

## 排查 robots、索引指令和规范链接

技术配置错误往往会造成整站或整目录异常。先访问：

```text
https://example.com/robots.txt
```

检查是否存在过宽的禁止规则，例如：

```txt
User-agent: *
Disallow: /
```

这会阻止允许遵守该协议的爬虫抓取全站。还要注意目录匹配错误，例如本想屏蔽后台，却把内容目录一并禁止。

检查页面源代码中是否误用了 robots 元标签：

```html
<meta name="robots" content="noindex, nofollow">
```

如果页面需要进入索引，应移除错误的 `noindex`。同时检查服务器是否通过 HTTP 响应头发送了类似的索引限制。

规范链接也需要核对：

```html
<link rel="canonical" href="https://example.com/correct-page/">
```

若 canonical 错误指向首页、其他文章或测试域名，搜索引擎可能将当前 URL 视为重复版本。canonical 通常属于规范化提示，并非绝对指令，但仍应保持自指或准确指向首选版本。

另外，不要同时使用“robots.txt 禁止抓取”和页面级 `noindex` 来处理同一 URL。爬虫被禁止抓取后，可能无法读取页面内的 `noindex`。确需让已收录页面退出时，应允许抓取并返回明确状态，再根据实际场景使用 `noindex`、404 或 410。

## 判断页面是否具有独立索引价值

技术上可抓取，不代表页面一定会被保留。百度需要从大量相似 URL 中选择具有独立价值的版本。

常见问题包括：

- 多个页面仅替换城市名、产品名，主体内容几乎相同；
- 标签页、筛选页、分页页大量生成，正文信息很少；
- 内容直接采集或拼接，没有新增事实、经验或解决步骤；
- 标题承诺与正文不一致；
- 页面被广告、弹窗或无关推荐占据；
- 同一内容同时存在多个参数 URL、打印版和移动版；
- 正文依赖客户端 JavaScript 请求，初始 HTML 几乎为空。

可以关闭 JavaScript或查看网页源代码，确认核心标题、正文、链接是否直接存在于返回的 HTML 中。对必须使用前端渲染的网站，可考虑服务端渲染或静态生成，但应先验证实际抓取结果，而不是仅凭浏览器显示正常作判断。

处理低价值页面时，不应简单追求“页面数量更多”。应合并重复主题、补充原创资料与操作细节，并让每个可索引页面对应明确需求。对筛选参数、站内搜索结果等页面，则应控制生成和内链暴露，避免浪费抓取资源。

## 改版、迁移和静态托管的专项检查

如果异常发生在域名更换、HTTPS 升级或 URL 结构调整之后，应建立旧 URL 与新 URL 的对应表，并逐条确认跳转。

推荐使用单次 `301` 或 `308` 永久重定向：

```text
旧 URL → 新 URL
```

避免出现：

```text
旧 URL → HTTP 中间地址 → HTTPS 首页 → 新 URL
```

还应同步更新站内链接、canonical、Sitemap 和分享链接，避免系统继续向搜索引擎暴露旧地址。不要把所有旧页面统一跳转到首页；内容不对应的跳转可能被视为软 404。

对于 GitHub Pages 等静态托管网站，需要特别检查：

- 自定义域名的 DNS 是否正确；
- 仓库中的 `CNAME` 配置是否与实际域名一致；
- HTTPS 是否可正常访问；
- 项目站点是否因基础路径配置错误导致资源或内链失效；
- 构建产物中是否真的包含目标页面；
- 大小写、尾斜杠和文件扩展名是否造成多个 URL 版本。

GitHub Pages 本身不提供服务器端自定义重定向规则。若迁移时需要大规模、可控的 HTTP 重定向，通常要借助支持重定向配置的 CDN、反向代理或其他托管服务，而不是只放一个 JavaScript 跳转页面。

## 按证据确定修复优先级

建议按“全站影响优先、抓取障碍优先”的顺序处理：

1. 修复 DNS、超时、`5xx`、全站 `403` 等可用性问题。
2. 删除错误的 robots 禁止规则和 `noindex`。
3. 修正异常跳转、软 404、错误 canonical。
4. 恢复重要页面的内链入口，更新 Sitemap 和提交链接。
5. 合并重复、空泛或批量生成的页面。
6. 持续观察服务器日志、抓取数据和索引量变化。

日志分析时，可按 User-Agent、请求 URL、状态码和时间聚合，但不要只依靠 User-Agent 判断真实蜘蛛，必要时还应进行 IP 反查与正向验证。修复后也不要频繁改动 URL、标题和页面结构，应给搜索引擎重新抓取与处理的时间。

收录异常很少靠单个“SEO 技巧”解决。最有效的诊断方式，是用响应状态、页面源代码、平台数据、服务器日志和改版记录建立证据链：先保证页面可发现、可访问、可理解，再判断内容是否具备独立保留价值。修复能够消除技术障碍，但无法保证页面一定收录或获得特定排名。
