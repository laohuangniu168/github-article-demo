# Soft 404问题检测与SEO修复方法

{% raw %}

## Soft 404 是什么，为什么需要处理

Soft 404 指页面看起来像“内容不存在”，但服务器没有返回正确的 `404 Not Found` 或 `410 Gone`，而是返回 `200 OK`、跳转到无关页面，或提供几乎没有有效内容的页面。

典型情况包括：

- 已删除商品仍返回 200，只显示“商品已下架”
- 不存在的 URL 统一跳转到首页
- 站内搜索无结果页返回 200，且可被抓取
- SPA 将所有未知路径都回退到同一个 `index.html`
- 页面主体为空，只剩导航、页脚和广告
- 接口报错后生成“暂无内容”，HTTP 状态仍为 200

搜索引擎可能根据页面内容自行将其判断为 Soft 404。此类 URL 通常不会被收录，还可能浪费抓取资源、干扰有效页面发现，并让站点的索引报告出现大量无价值地址。

需要注意，内容较短不等于 Soft 404。联系方式、术语解释等页面即使篇幅不长，只要满足明确需求，仍可能是有效页面。

## 如何检测 Soft 404

### 1. 查看 Google Search Console

进入 Google Search Console 的“网页索引”报告，在“未编入索引”的原因中查找“Soft 404”。打开具体示例 URL，重点检查：

- URL 是否本应存在
- 页面当前返回什么状态码
- Google 抓取时看到的内容
- 是否发生跳转
- 页面是否依赖 JavaScript 才能显示主体内容

示例 URL 只是抽样，并不一定包含全部问题地址。修复后可以发起验证，但报告更新取决于 Google 再次抓取和处理，不会立即变化。

### 2. 检查真实 HTTP 状态

可使用 `curl` 查看响应：

```bash
curl -I https://example.com/not-exist-page
```

也可以同时输出最终状态码和跳转目标：

```bash
curl -s -o /dev/null \
  -w "status=%{http_code} redirect=%{redirect_url}\n" \
  https://example.com/not-exist-page
```

判断结果时不要只检查状态码，还要查看正文。一个返回 200、正文却只有“页面不存在”的 URL，仍是典型 Soft 404。

如果页面存在重定向，可使用以下命令跟随跳转：

```bash
curl -L -I https://example.com/old-page
```

### 3. 使用爬虫和日志批量排查

Screaming Frog、Sitebulb 等爬虫可以找出：

- 标题或正文包含“未找到”“暂无内容”的 200 页面
- 内容字数异常少的页面
- 大量跳转到首页的旧 URL
- 重复标题、重复模板和空白页面

服务器日志则能发现搜索引擎频繁访问但没有价值的参数 URL、错误路径和历史地址。将日志中的高频 URL 与状态码、页面内容结合分析，比单纯扫描站内链接更全面。

## 先判断 URL 应该保留、替代还是删除

修复前需要明确页面的实际用途，不应把所有 Soft 404 都改成同一种状态。

| 页面情况 | 建议处理 |
|---|---|
| URL 输入错误或从未存在 | 返回 404 |
| 内容永久删除且不会恢复 | 返回 404 或 410 |
| 已有高度相关的新页面 | 301 重定向到对应新页面 |
| 页面本应存在但内容加载失败 | 修复数据、模板或接口 |
| 商品暂时缺货，未来会恢复 | 保留 200，并展示有价值信息 |
| 站内搜索没有结果 | 通常保留给用户，但设置 `noindex`，避免大量索引 |
| 服务暂时故障或维护 | 返回 503，而不是伪装成 404 |

`404` 与 `410` 都可用于永久不可用的内容。410 明确表示资源已移除，但不代表搜索引擎一定会按固定速度删除索引。

不要把大量失效 URL 全部 301 到首页。重定向目标与原页面缺乏对应关系时，搜索引擎仍可能将其视为 Soft 404。只有存在真正替代内容时，301 才合理。

## 常见场景的修复方法

### 返回正确的错误状态

Nginx 可以配置自定义错误页，同时保留 404 状态：

```nginx
error_page 404 /404.html;

location = /404.html {
    internal;
}
```

不要使用会把错误页改成 200 的写法，例如：

```nginx
error_page 404 =200 /404.html;
```

Apache 可使用：

```apache
ErrorDocument 404 /404.html
```

应用程序也应在确认资源不存在时设置 HTTP 状态，而不只是渲染一段错误提示。以伪代码表示：

```text
if resource does not exist:
    response.status = 404
    render("404")
```

自定义 404 页面可以包含搜索框、首页入口和相关栏目，但不要让它与正常内容页完全相同，也不必通过 `robots.txt` 禁止抓取。搜索引擎需要访问该页面，才能确认它确实返回 404。

### 修复有价值但内容过少的页面

如果 URL 本应参与搜索，应优先补齐真实内容，而不是机械增加字数。可检查：

- 主体数据是否因接口错误未输出
- 商品名称、规格、价格或库存是否缺失
- 分类页是否只有筛选器，没有项目列表
- JavaScript 渲染失败时是否只剩空模板
- 页面是否错误地向未登录用户隐藏全部内容

如果确实没有足够的独立价值，可合并到相关页面并设置 301，或删除后返回 404/410。

### 处理 SPA 和静态托管路由

SPA 常将任意路径都返回 `index.html` 和 200。浏览器虽然显示“未找到”，但 HTTP 响应已经成功，前端 JavaScript 无法事后修改服务器状态码。

可选方案包括：

1. 在服务器、边缘函数或 SSR 框架中验证路由；
2. 有效路由返回 200，无效路由返回 404；
3. 对不需要搜索收录的纯客户端页面设置合理的索引策略；
4. 不要无限生成可访问但无内容的动态路径。

GitHub Pages 支持在发布源根目录放置 `404.html` 作为自定义错误页。不存在的静态文件会由平台返回 404，并展示该文件内容。不要通过脚本把所有未知路径强制跳转到首页，也不要把正常首页简单复制成错误页，否则可能导致识别混乱。

## 修复后的验证流程

完成修改后，建议按以下顺序复查：

1. 随机测试多个不存在的 URL，而不只测试一个固定地址；
2. 确认最终响应是 404、410 或合理的 301；
3. 查看响应正文，避免错误模板再次返回空白内容；
4. 检查站内链接、站点地图和 canonical 是否仍指向失效 URL；
5. 对应删除 XML Sitemap 中不可索引的地址；
6. 在 Search Console 使用 URL 检查工具测试实时网址；
7. 等待重新抓取，并观察 Soft 404 数量是否下降。

还应测试带参数、大小写变化、尾部斜杠和随机路径，例如：

```text
/product/not-exist
/product/not-exist?ref=test
/PRODUCT/NOT-EXIST
/product/not-exist/
```

如果不同变体返回结果不一致，说明路由规则可能仍有漏洞。

## 降低问题再次出现的概率

日常发布流程中，可以自动监控站点地图 URL 的状态码，检查页面主体是否为空，并在删除内容时同步更新内部链接。电商或内容平台还应预先定义下架、合并、暂时缺货和永久删除的处理规则。

Soft 404 的修复重点不是让报告中的数字立即归零，而是让每个 URL 的状态与实际内容一致：存在且有价值的页面返回 200，有明确替代页面时进行相关重定向，永久不存在的资源返回 404 或 410。这样既能改善用户访问体验，也能让搜索引擎更准确地理解站点结构。
