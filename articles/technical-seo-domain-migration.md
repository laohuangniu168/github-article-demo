# 域名更换SEO迁移完整指南

{% raw %}

更换域名并不是简单地修改 DNS。搜索引擎需要重新发现新网址、确认永久跳转关系，并将旧域名积累的索引与链接信号逐步迁移到新域名。整个过程无法保证排名完全不波动，但通过规范实施，可以减少抓取错误和流量损失。

## 迁移前先建立完整基线

不要在上线当天才开始整理网址。迁移前应记录网站当前状态，方便迁移后判断问题来自域名变化，还是网站本身的技术故障。

建议至少准备以下数据：

- 导出搜索引擎自然流量、关键词、着陆页和转化数据。
- 从 Google Search Console、Bing Webmaster Tools 导出收录、点击和外链数据。
- 抓取全站 URL，记录状态码、标题、Canonical、Meta Robots 和内链数量。
- 保存现有 XML Sitemap、robots.txt、结构化数据和重要页面模板。
- 列出高流量页面、高价值外链页面及主要转化页面。
- 确认新域名没有搜索引擎处罚、垃圾历史或异常外链。

可通过搜索引擎检索新域名，结合互联网存档和外链工具检查历史用途。如果该域名过去被用于仿冒、采集或灰色业务，即使当前内容为空，也可能增加迁移风险。

同时确定迁移范围。风险最低的方案通常是**只更换域名，保持协议、路径、参数、内容和页面结构不变**。不要同时进行大规模改版、URL 重构、CMS 更换和内容删减，否则出现流量波动时很难定位原因。

## 制作旧 URL 到新 URL 的映射

每个有价值的旧网址都应跳转到内容最接近的新网址，而不是全部重定向到首页。

如果仅更换域名，可以按原路径一一对应：

```text
https://old.example.com/products/a
→ https://new.example.com/products/a
```

如果路径也发生变化，应建立明确的映射表：

| 旧 URL | 新 URL | 处理方式 |
|---|---|---|
| `/about-us` | `/about` | 301 |
| `/blog/old-post` | `/guides/new-post` | 301 |
| `/expired-campaign` | 无替代页面 | 410 或保留说明页 |

无法找到等价内容时，不要为了“传递权重”强行跳转到首页。大量无关跳转可能被搜索引擎视为软 404，也会影响用户体验。真正永久删除且没有替代内容的页面，可以返回 404 或 410。

映射时还要覆盖：

- HTTP、HTTPS、带 `www` 和不带 `www` 的旧地址；
- 大小写不同、末尾斜杠不同的 URL；
- 图片、PDF 等仍有外链或搜索流量的资源；
- 带查询参数的有效页面；
- 历史上已经重定向过的旧路径。

目标是让任意旧 URL 通过一次跳转到达最终新 URL，避免“旧地址→中间地址→新地址”的重定向链。

## 配置永久重定向与域名基础设施

域名迁移通常使用服务端 `301 Moved Permanently`。`308` 同样表示永久重定向，但 301 的使用更普遍。不要使用 JavaScript 跳转、定时刷新或仅在页面中放置新域名链接来替代服务端重定向。

Nginx 保留原路径的示例：

```nginx
server {
    listen 80;
    listen 443 ssl;
    server_name old.example.com www.old.example.com;

    return 301 https://new.example.com$request_uri;
}
```

Apache 可使用：

```apache
RewriteEngine On
RewriteCond %{HTTP_HOST} ^(www\.)?old\.example\.com$ [NC]
RewriteRule ^(.*)$ https://new.example.com/$1 [R=301,L]
```

上线前应确认：

1. 新旧域名的 DNS 均能正常解析；
2. 两个域名都具有有效 HTTPS 证书；
3. 旧域名的服务器或跳转服务能够长期保留；
4. 跳转后的页面返回 `200`，而不是再次跳转或报错；
5. 查询参数是否按业务需要保留；
6. CDN 缓存不会继续返回旧规则。

可以使用命令检查响应链：

```bash
curl -I https://old.example.com/example-page
curl -IL https://old.example.com/example-page
```

旧域名至少应保留数年，条件允许时长期续费。过早停用会导致外链失效，也可能让域名被他人注册并带来品牌或安全风险。

### GitHub Pages 的特殊情况

GitHub Pages 可以绑定自定义域名，但不能像 Nginx 一样自由配置任意服务器级 301 规则。仓库中的 `CNAME` 文件用于声明自定义域名，并不负责把旧自定义域名永久跳转到新域名。

如果站点使用 GitHub Pages，更换自定义域名后，可让旧域名继续接入支持重定向规则的 DNS/CDN 服务，或将旧域名指向单独的轻量服务器执行 301。不要仅修改仓库的自定义域名设置后就假定旧域名会自动、长期地跳转到新域名。

## 更新站内 SEO 与第三方配置

即使已经设置 301，站内仍应直接引用新域名，避免搜索引擎和用户经过不必要的跳转。

需要批量检查并更新：

- 导航、正文、面包屑、分页和页脚中的内部链接；
- `rel="canonical"` 指向的新域名 URL；
- Hreflang 中的所有语言和地区版本；
- XML Sitemap 内的网址；
- Open Graph、Twitter Card 和结构化数据中的绝对地址；
- 图片、脚本、样式表、API 与下载文件地址；
- robots.txt 中声明的 Sitemap 地址；
- 表单提交、登录回调、支付通知和跨域白名单；
- 邮件模板、广告落地页及社交媒体资料。

新站页面应采用自引用 Canonical，例如：

```html
<link rel="canonical" href="https://new.example.com/products/a">
```

不要让新页面的 Canonical 继续指向旧域名，否则会向搜索引擎发送相互矛盾的信号。

确认 robots.txt 没有屏蔽重要目录，新站也不能残留测试环境常见的 `noindex`。旧域名的 URL 需要允许搜索引擎访问，爬虫只有访问到旧地址，才能看到 301；不要用 robots.txt 阻止整个旧站。

## 通知搜索引擎并安排上线

迁移上线前，先在 Google Search Console 中验证新旧域名相关资源的所有权。正式切换并确认重定向可用后，可在旧站资源中使用“地址更改”工具提交域名变更。该工具是辅助信号，不能代替逐页 301。

同时应：

- 在新域名对应的 Search Console 资源中提交新 Sitemap；
- 在 Bing Webmaster Tools 中验证新站，并使用其站点迁移相关功能；
- 更新分析工具、广告平台和站长工具中的域名设置；
- 联系重要合作方，将高价值外链直接更新为新 URL；
- 在访问量相对稳定的时段上线，并安排技术人员持续观察。

迁移初期可以保留并提交包含旧 URL 的旧 Sitemap，帮助搜索引擎重新抓取旧地址并发现重定向；新 Sitemap 则只应包含可索引、返回 200 且 Canonical 指向自身的新 URL。待旧 URL 的索引和抓取量明显下降后，再移除旧 Sitemap。

## 上线后的检查与异常处理

域名更换后出现短期抓取和排名波动并不罕见。监控重点不是某一天的关键词位置，而是搜索引擎能否稳定访问、理解并索引新网址。

上线后应定期检查：

- 旧 URL 是否全部返回一次性 301；
- 新站是否出现 404、5xx、软 404 或重定向循环；
- 新 URL 的收录量和自然流量变化；
- Search Console 中的网页索引、抓取统计和重复页面报告；
- Sitemap 提交数、发现数与实际收录差异；
- 服务器日志中搜索引擎爬虫对新旧域名的访问情况；
- 重要页面的 Canonical 是否被搜索引擎正确选择；
- 转化、登录、结算、表单和站内搜索是否正常。

如果大量新页面未收录，应先排查 robots.txt、`noindex`、Canonical、服务器稳定性和内容可访问性，而不是频繁修改域名或反复提交。若流量集中下降在某一目录，通常需要检查该目录的映射规则、模板配置和内链更新情况。

域名迁移的核心是保持信号一致：旧网址永久跳转到对应的新网址，站内链接和 Canonical 统一指向新域名，搜索引擎能够正常抓取两端。提前建立映射、控制变更范围并持续监控，比上线后依赖补救更可靠。
