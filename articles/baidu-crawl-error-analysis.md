# 百度蜘蛛抓取异常分析与排查方法

{% raw %}

百度蜘蛛抓取异常，通常表现为百度搜索资源平台诊断失败、服务器日志中大量 4xx/5xx、页面长期无法更新，或 Baiduspider 请求频率突然下降。排查时不要先入为主地认为是“百度不抓”，而应确认请求在哪个环节中断。

需要注意：抓取成功只表示搜索引擎能够访问页面，并不等于页面一定会被收录或获得排名。

## 先判断属于哪一类抓取异常

抓取链路大致经过 DNS 解析、网络连接、HTTPS 握手、服务器或 CDN、安全策略、页面响应等环节。常见异常可以按现象分类：

| 异常现象 | 常见原因 |
| --- | --- |
| DNS 解析失败 | 域名过期、解析记录错误、DNS 服务不稳定 |
| 连接超时 | 服务器负载过高、防火墙拦截、跨地域网络不稳定 |
| 返回 403 | WAF、访问频率限制、User-Agent 规则误伤 |
| 返回 404/410 | URL 已删除、路径变更、伪静态规则错误 |
| 返回 500/502/503/504 | 程序报错、上游服务不可用、服务器过载 |
| 重定向异常 | 循环跳转、跳转次数过多、HTTP 与 HTTPS 规则冲突 |
| 抓到空白或错误内容 | JavaScript 渲染依赖、接口故障、按来源返回不同页面 |
| robots 禁止抓取 | robots.txt 规则写错，或目录范围判断错误 |

如果只是个别 URL 异常，优先检查页面本身、重定向和程序逻辑；如果全站 URL 同时异常，则应先查 DNS、证书、服务器、防火墙及 CDN。

## 使用抓取诊断和命令行复现问题

可以先在百度搜索资源平台验证站点，并使用平台提供的抓取诊断类工具测试典型 URL。工具入口名称可能调整，但重点是观察抓取结果、HTTP 状态和返回内容。

同时，应从站外网络直接测试 URL：

```bash
curl -I -L --max-redirs 10 https://www.example.com/page.html
```

参数含义：

- `-I`：只获取响应头；
- `-L`：跟随重定向；
- `--max-redirs 10`：限制跳转次数，便于发现循环跳转。

还可以模拟蜘蛛的 User-Agent，判断服务器是否存在差异化响应：

```bash
curl -A "Baiduspider" -I https://www.example.com/page.html
curl -A "Baiduspider" https://www.example.com/page.html -o baidu.html
```

将普通浏览器请求与上述结果对比。如果浏览器返回 200，而 Baiduspider 返回 403、验证码或空白页，通常说明 CDN、WAF、反爬组件或程序中的 User-Agent 规则发生了误拦截。

检查时不能只看最终状态码。例如下面的链路虽然最终为 200，但仍可能增加抓取失败概率：

```text
http://example.com/a
→ https://example.com/a
→ https://www.example.com/a
→ https://www.example.com/a/
→ 200
```

应尽量将常用入口直接跳转到唯一规范地址，避免多级跳转和循环跳转。

## 从服务器日志确认蜘蛛是否到达

服务器访问日志比站长后台更接近真实请求。Nginx 环境可先筛选包含 Baiduspider 的记录：

```bash
grep -i "Baiduspider" /var/log/nginx/access.log | tail -n 100
```

统计相关状态码：

```bash
grep -i "Baiduspider" /var/log/nginx/access.log \
  | awk '{print $9}' | sort | uniq -c | sort -nr
```

重点查看以下字段：

- 请求时间和 URL；
- HTTP 状态码；
- 响应字节数；
- User-Agent；
- 来源 IP；
- 请求处理时间；
- 上游响应时间。

如果日志中完全没有对应请求，而平台提示无法抓取，问题可能发生在 DNS、网络、防火墙或 CDN 层。如果访问日志中有请求，但大量返回 5xx，则需要继续检查 Nginx 错误日志、应用日志及数据库状态。

User-Agent 可以伪造，不能仅凭字符串认定请求来自百度。需要确认来源时，可对 IP 做反向 DNS 查询，再对所得域名执行正向解析，核对是否回到原 IP。不要直接根据网络上流传的固定 IP 列表永久放行，因为蜘蛛地址范围可能变化。

## 检查 robots.txt、状态码和页面可访问性

robots.txt 位于站点根目录，例如：

```text
https://www.example.com/robots.txt
```

常见误配置包括：

```text
User-agent: *
Disallow: /
```

这会禁止所有遵守 robots 协议的爬虫抓取全站。另一个容易忽略的问题是目录规则范围过大：

```text
User-agent: Baiduspider
Disallow: /article/
```

如果核心内容都位于 `/article/`，百度蜘蛛将无法抓取这些页面。修改后还要确认 robots.txt 本身能够稳定返回 `200`，没有登录验证或重定向到 HTML 错误页。

状态码也要与页面含义一致：

- 正常页面返回 `200`；
- 永久迁移通常使用 `301`；
- 临时调整可使用 `302`，但不宜长期滥用；
- 已删除且无替代内容的页面返回 `404` 或 `410`；
- 维护期间可返回 `503`，并尽量提供合理的 `Retry-After`；
- 不要让错误页面显示“内容不存在”却仍返回 `200`，这属于软 404。

还应检查页面是否必须执行复杂 JavaScript 才能出现正文。对于重要内容，建议在初始 HTML 中提供可读取的标题、正文和链接，不要让核心信息完全依赖前端接口异步加载。

## 排查 CDN、WAF 和服务器稳定性

CDN 或安全防护是抓取异常的高发环节。常见问题包括：

1. 将蜘蛛请求判定为恶意机器人，返回 403 或验证码；
2. 按访问频率封禁 IP，导致连续抓取失败；
3. 境内外节点配置不一致，同一 URL 返回不同内容；
4. CDN 回源超时，产生 502 或 504；
5. HTTPS 证书链不完整，部分客户端握手失败；
6. 开启强制登录、Cookie 校验或 JavaScript 挑战。

排查时可临时建立受控测试规则，而不是直接关闭全部防护。对确认过身份的蜘蛛请求放行后，继续观察访问日志与错误率，避免把伪造 User-Agent 的请求一并放开。

服务器方面应检查 CPU、内存、连接数、磁盘 I/O、PHP 或 Java 进程池、数据库慢查询等指标。如果 5xx 集中在固定时间段，可能与备份任务、定时生成页面或流量高峰有关。

DNS 也需要单独验证：

```bash
dig example.com A
dig www.example.com A
dig example.com AAAA
```

确认根域名与 `www` 记录正确，IPv6 地址确实可访问。如果配置了 AAAA 记录，但服务器的 IPv6 网络不可用，部分请求可能连接失败。

## 修复后的验证与持续监控

修复后不要只测试首页，应选择多种页面进行验证：

- 首页；
- 栏目页；
- 新发布内容页；
- 历史内容页；
- 带参数 URL；
- 曾经返回 4xx 或 5xx 的 URL；
- HTTP、HTTPS、根域名和 `www` 入口。

确认这些页面能返回预期状态码、正文完整、跳转链简洁，并且没有被 robots.txt 禁止。随后在百度搜索资源平台重新执行诊断，观察服务器日志中蜘蛛请求的状态码和响应时间是否恢复正常。

长期监控可以设置以下指标：

- Baiduspider 每日请求量；
- 2xx、3xx、4xx、5xx 的占比；
- 平均响应时间和超时数量；
- robots.txt 可用性；
- DNS 与 HTTPS 证书状态；
- 重点页面的内容长度及状态码变化。

抓取恢复后，收录变化通常还需要等待搜索引擎重新访问和处理页面。与其频繁修改 URL 或重复提交，不如保持服务器稳定、状态码准确、内部链接可达，并持续减少蜘蛛实际遇到的访问障碍。
