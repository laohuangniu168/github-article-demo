# 百度蜘蛛抓取模式复盘与异常识别方法

{% raw %}

## 先明确复盘对象：抓取不等于收录

百度蜘蛛[抓取](./baidu-crawl-error-analysis.html)复盘的核心，是回答三个问题：

1. 蜘蛛什么时候访问了网站；
2. 它抓取了哪些 URL，服务器如何响应；
3. 当前行为与历史基线相比是否异常。

抓取、索引和搜索展现是不同环节。日志中出现 `Baiduspider`，只能说明某个客户端发起了请求，不能直接证明页面已经收录；抓取量增加，也不代表排名一定提升。

建议优先准备以下数据：

- CDN 或源站访问日志；
- 最近一次改版、迁移和规则调整时间；
- `robots.txt`、站点地图及重定向配置；
- 百度搜索资源平台中可用的抓取、索引相关数据；
- 服务器监控中的响应时间、CPU、内存和错误率。

如果网站使用 CDN，应优先查看边缘节点日志。源站日志可能只记录 CDN 回源 IP，无法完整还原蜘蛛访问情况。若使用 `X-Forwarded-For`，还要确认该字段由可信代理写入，不能直接相信客户端自行提交的请求头。

## 从日志建立可比较的抓取基线

常见 Nginx Combined 日志大致如下：

```text
123.45.67.89 - - [12/Mar/2025:03:18:20 +0800] "GET /article/a.html HTTP/1.1" 200 18342 "-" "Mozilla/5.0 ... Baiduspider ..."
```

至少应提取这些字段：

- 请求时间；
- 客户端 IP；
- User-Agent；
- 请求方法与 URL；
- HTTP 状态码；
- 响应字节数；
- 响应耗时；
- Referer；
- 命中的主机名或虚拟站点。

可以先筛选包含百度[蜘蛛](./baidu-crawl-rate-monitoring.html)标识的记录：

```bash
grep -i "Baiduspider" access.log > baidu-spider.log
```

再按状态码做粗略统计：

```bash
awk '{print $9}' baidu-spider.log | sort | uniq -c | sort -nr
```

不过，单日请求总数通常意义有限。更实用的基线应按天或按周统计：

| 指标 | 用途 |
|---|---|
| 请求次数、独立 URL 数 | 观察整体抓取规模 |
| 2xx、3xx、4xx、5xx 占比 | 判断响应质量 |
| 目录与页面类型分布 | 识别抓取资源是否偏移 |
| 重复抓取率 | 发现参数页、分页或重复 URL |
| 平均值与 P95 响应时间 | 识别性能异常 |
| 首次抓取与再次抓取间隔 | 观察内容更新后的发现速度 |
| 每小时请求量 | 识别突发流量和时间段变化 |

基线至少覆盖几个完整业务周期。例如资讯站应包含工作日和周末，电商站还应避开仅用促销日数据作为常态。网站规模、更新频率不同，不适合套用统一的“正常抓取量”。

## 用多个维度还原抓取模式

复盘时不要只画一条请求量曲线，还要把流量拆开。

### 按页面类型拆分

可将 URL 分为首页、栏目页、内容页、分页、筛选页、站内搜索页、静态资源和接口。理想状态不是所有页面均匀被抓，而是重要且可索引的页面能够被稳定发现。

若大量请求集中在以下 URL，应进一步检查：

- 带会话 ID 或追踪参数的地址；
- 无限组合的筛选与排序页面；
- 日历翻页、站内搜索结果；
- 内容相同但路径不同的 URL；
- 已删除却持续被内链或站点地图引用的地址。

### 按状态码拆分

不同[状态码](./baidu-crawl-status-code-analysis.html)反映的问题并不相同：

- `200`：请求成功，但仍需确认是否返回真实正文，而不是软 404；
- `301/308`：永久重定向，需检查是否存在多跳链路；
- `302/307`：临时重定向，长期存在时应核对使用意图；
- `304`：缓存协商结果，不等同于抓取失败；
- `403`：可能被 WAF、频率限制或权限规则拦截；
- `404/410`：页面不存在，应确认是否仍被内链或站点地图提交；
- `429`：服务器主动限流；
- `5xx`：服务端错误，尤其要关注持续时间和受影响目录。

### 按时间与响应性能拆分

将每小时抓取量与服务器 P95 响应时间、5xx 比例放在同一时间轴上。若蜘蛛请求下降前已经出现超时或错误增长，应优先检查服务稳定性，而不是立即修改页面内容。

## 识别几类常见异常

### 抓取量突然下降

先排除日志缺失、日志轮转、CDN 切换和时区变化，再检查：

1. `robots.txt` 是否误封目录或全站；
2. 是否增加登录、验证码、地域或 IP 限制；
3. HTTPS、域名或 URL 迁移后是否存在证书和重定向问题；
4. 站点地图是否仍能访问，且 URL 是否为最终规范地址；
5. 重要页面是否失去内链入口；
6. 服务器是否频繁超时、返回 403、429 或 5xx。

需要注意，`canonical` 用于表达规范版本，并不是阻止抓取的指令；如果确实不希望某类路径被抓，应结合页面价值、内链和 `robots.txt` 谨慎处理。

### 抓取量突然暴增

暴增不一定是好事。应查看新增请求是否集中于参数页、分页、错误 URL 或重定向链。程序上线后生成大量可遍历链接，常会导致蜘蛛进入近似无限的 URL 空间。

可重点统计去掉查询参数后的 URL 数量，并检查参数组合：

```text
/list?sort=new&page=2
/list?sort=hot&page=2
/list?sort=new&page=2&utm_source=x
```

如果这些页面内容高度重复，应从链接生成逻辑、参数规范、站点地图和必要的抓取限制等方面处理，而不是只在日志层面屏蔽。

### 请求正常但有效页面减少

这种情况常见于软 404、空模板、异常跳转或前端渲染失败。服务器虽然返回 `200`，正文可能只有“内容不存在”或空白框架。抽样访问高频 URL，核对页面标题、正文、状态码和最终跳转地址，通常比只看报表更有效。

## 校验蜘蛛身份，避免被伪造 UA 误导

User-Agent 可以被任意客户端伪造，因此不能仅凭字符串认定请求来自百度蜘蛛。较稳妥的方法是对来源 IP 做反向 DNS 查询，再对所得域名做正向解析，确认解析结果能够回到原 IP，同时参照百度官方公布的识别说明。

示例流程：

```bash
host 123.45.67.89
host 返回的主机名
```

判断时应满足：

1. 反向解析得到的域名符合官方说明；
2. 对该域名进行正向解析；
3. 正向解析结果包含原始请求 IP。

不要只根据一个看似相关的主机名放行，也不要长期维护来源不明的固定 IP 列表。搜索引擎网络范围可能调整，验证规则应以百度当时的官方文档为准。

如果疑似伪造请求造成资源消耗，可在 WAF 或网关层限速，但应避免仅按 User-Agent 大范围封禁，以免误伤真实抓取或普通用户。

## 建立“发现—验证—修复—观察”的闭环

发现异常后，建议按以下顺序处理：

1. **确认数据可信**：核对日志是否完整，过滤内部监控、缓存回源和伪造 UA。
2. **确定异常范围**：明确发生时间、目录、状态码、IP 和页面类型。
3. **对照变更记录**：检查发布、迁移、CDN、WAF、模板和链接规则变化。
4. **抽样复现**：使用浏览器及命令行检查响应头、跳转链和正文。
5. **修复根因**：优先解决错误响应、无限 URL、断链和[性能](./baidu-crawl-response-time.html)问题。
6. **持续观察**：至少跨越若干抓取周期，对比修复前后的同口径指标。

复盘报告应保留异常时间线、影响 URL 样本、证据日志、变更项和观察结果。百度蜘蛛的访问节奏可能受站点更新、服务器状态和搜索系统调度等多种因素影响，因此不宜根据一两天的波动下结论。真正有价值的异常识别，是在可靠日志、历史基线和配置变更之间建立可验证的对应关系。
