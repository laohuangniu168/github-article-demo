# GitHub Pages文章内链优化方法

GitHub Pages 的文章内链不仅用于引导读者继续浏览，也能帮助搜索引擎发现页面、理解内容关系。优化的重点不是增加链接数量，而是建立清晰的内容结构，并确保链接在项目站点、自定义域名和本地预览环境中都能正确访问。

## 先确认 GitHub Pages 的 URL 结构

GitHub Pages 常见的部署形式有两种：

- 用户或组织站点：`https://username.github.io/`
- 项目站点：`https://username.github.io/repository/`

两者最大的区别是项目站点通常带有仓库路径。如果直接将内链写成：

```markdown
[配置教程](/config/)
```

浏览器会把它解析为：

```text
https://username.github.io/config/
```

但项目页面的实际地址可能是：

```text
https://username.github.io/repository/config/
```

这样就会产生 404。

使用 Jekyll 构建时，可以在 `_config.yml` 中设置：

```yaml
url: "https://username.github.io"
baseurl: "/repository"
```

用户站点或部署在域名根目录时，通常将 `baseurl` 设为空字符串：

```yaml
url: "https://example.com"
baseurl: ""
```

具体值应以网站的真实访问路径为准。修改 `_config.yml` 后，本地运行中的 Jekyll 服务通常需要重新启动才能读取新配置。

## 使用 Jekyll 过滤器生成稳定内链

对于启用了 Jekyll 的 GitHub Pages，推荐使用 `relative_url` 过滤器，而不是手工拼接仓库名称：

```markdown
[查看安装指南]({{ '/guide/install/' | relative_url }})
```

生成项目站点时，它会自动补充 `baseurl`；切换到自定义域名或根目录部署后，也不必逐篇修改链接。

链接到已发布文章时，可以使用 `post_url`：

```markdown
[阅读完整配置方法]({% post_url 2024-05-20-github-pages-config %})
```

其中的文件名应与 `_posts` 目录中的文章文件一致，但不包含扩展名。与直接填写最终 URL 相比，`post_url` 能在构建阶段检查目标文章是否存在，文章永久链接发生调整时也更容易维护。

链接到普通页面或集合文档，可以使用 `link` 标签：

```markdown
[关于本站]({% link about.md %})
```

如果站点没有使用 Jekyll，而是直接发布静态 HTML，则无法依赖这些 Liquid 标签。这种情况下应根据部署目录使用正确的相对路径，例如：

```html
<a href="../guide/install/">安装指南</a>
```

不要在 Markdown 中混用本地文件系统路径，如 `C:\blog\post.md`，它们在 GitHub Pages 上无法访问。

## 建立主题清晰的内链结构

有效的内链应体现内容之间的关系，而不是在每篇文章底部机械列出大量链接。可以将网站组织为三层：

1. **主题入口页**：集中介绍某个主题并链接到详细文章。
2. **细分教程页**：解决具体问题，并返回主题入口。
3. **补充内容页**：解释命令、故障排查或使用案例。

例如，围绕 GitHub Pages 建站，可以设置一个“GitHub Pages 完整指南”入口页，再链接到域名绑定、HTTPS、Jekyll 配置和部署错误排查等文章。细分文章之间只有在确实相关时才互相推荐。

发布新文章后，可以完成两项操作：

- 从一至三篇已有的相关页面链接到新文章，避免新页面成为孤立页面。
- 在新文章中链接到必要的基础教程或上级主题页，补充阅读路径。

导航栏、分类页和正文链接的作用并不完全相同。导航栏负责展示核心栏目，正文内链则能通过上下文说明两篇内容为什么相关。对于重要教程，最好不要只依赖标签页或归档页提供入口。

## 编写准确而自然的锚文本

锚文本应让读者在点击前知道目标页面讲什么。下面的写法信息不足：

```markdown
更多内容请[点击这里]({{ '/domain/' | relative_url }})。
```

更清晰的写法是：

```markdown
如果准备使用独立域名，可继续阅读
[GitHub Pages 自定义域名配置方法]({{ '/domain/' | relative_url }})。
```

锚文本优化可以遵循以下原则：

- 使用能够概括目标内容的短语。
- 将链接放进自然语句，不要单独堆放关键词。
- 同一页面中避免反复链接到相同目标。
- 不要为了覆盖更多词语而写过长、重复的锚文本。
- 只有在确有补充价值时才添加链接。

站内普通链接通常不需要添加 `rel="nofollow"`。同时，不建议通过必须执行 JavaScript 才能生成的点击事件代替标准 `<a href="...">` 链接，因为标准链接更容易被浏览器、辅助工具和搜索引擎识别。

## 统一永久链接并减少失效页面

如果文章 URL 经常变化，旧内链会逐渐失效。可以在 `_config.yml` 中统一设置文章永久链接规则，例如：

```yaml
permalink: /:categories/:title/
```

也可以为单篇文章设置固定的 `permalink`。不过，一旦页面已经公开并被引用，就不应仅为了让 URL 更短而频繁更改。

需要特别注意以下差异：

- `/guide/` 与 `/guide/index.html`
- `/guide` 与 `/guide/`
- 文件名大小写差异
- 中文文件名的编码形式
- 更换分类后产生的路径变化

GitHub Pages 本身不提供可自由配置的服务器端 301 重定向规则。改动已发布 URL 前，应先评估旧地址的访问和引用情况。若必须迁移，可保留旧页面并提供明确的新地址入口，但 HTML 跳转页不能完全等同于服务器端 301。

站点是否带 `.html`、是否使用尾部斜杠，应按照实际生成结果统一处理。不要仅凭源码文件名猜测最终 URL，可以在 `_site` 目录或部署完成的网站中确认。

## 定期检查链接与优化效果

每次调整目录、文件名、分类或 `permalink` 后，都应执行一次内部链接检查。基本流程如下：

1. 在本地运行 Jekyll 构建。
2. 检查 `_site` 中是否生成目标页面。
3. 抽查导航、正文链接和目录锚点。
4. 查找返回 404 的内部地址。
5. 部署后再次检查带 `baseurl` 的真实路径。

可以使用静态链接检查工具扫描构建后的 `_site` 目录，也可以在 GitHub Actions 中加入链接检查步骤。使用第三方 Action 时，应先阅读其文档并固定可信版本，避免直接复制来源不明的工作流配置。

优化完成后，可结合 GitHub Pages 的访问统计方案或 Google Search Console 等工具观察：

- 重要页面是否能从其他页面到达；
- 新文章是否长期没有内部入口；
- 用户是否会继续访问相关教程；
- 抓取报告中是否出现大量 404；
- 站点地图中的 URL 与正文链接是否一致。

这些数据只能用于判断结构是否更合理，不能证明某次内链修改一定会带来排名变化。真正可持续的做法，是使用适配部署路径的链接语法，以主题关系组织文章，并在 URL 变更后及时修复旧链接。
