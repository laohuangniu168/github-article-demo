# 百度蜘蛛HTTP状态码日志分析方法

{% raw %}

## 分析前先确认日志记录完整

百度蜘蛛访问网站时，服务器通常会在访问日志中留下请求时间、URL、HTTP 状态码、User-Agent、来源 IP、响应字节数和耗时等信息。分析状态码的前提，是日志没有被 CDN、反向代理或缓存层截断。

以 Nginx 为例，可以使用包含响应时间的日志格式：

```nginx
log_format seo '$remote_addr - $remote_user [$time_local] '
               '"$request" $status $body_bytes_sent '
               '"$http_referer" "$http_user_agent" '
               'rt=$request_time';

access_log /var/log/nginx/access.log seo;
```

修改配置后，应先执行 `nginx -t` 检查语法，再平滑加载配置。历史日志不会因修改格式而补充字段，因此趋势分析需要从新格式生效后开始。

如果网站接入了 CDN，应优先使用 CDN 提供的原始访问日志，或确认源站已正确记录访客真实 IP。否则，源站日志中的 IP 可能只是 CDN 回源节点，无法直接用于蜘蛛身份核验。

Apache 常见日志中也会记录状态码和 User-Agent，例如：

```text
220.181.xx.xx - - [12/Mar/2025:09:15:02 +0800] "GET /article/123 HTTP/1.1" 200 8421 "-" "Mozilla/5.0 (compatible; Baiduspider/2.0; +http://www.baidu.com/search/spider.html)"
```

其中 `200` 是响应状态，`/article/123` 是抓取 URL，最后一段是 User-Agent。

## 正确识别百度蜘蛛请求

最直接的方法是筛选 User-Agent 中包含 `Baiduspider` 的记录：

```bash
grep -i 'Baiduspider' /var/log/nginx/access.log
```

保存到单独文件后再分析：

```bash
grep -i 'Baiduspider' /var/log/nginx/access.log > baiduspider.log
```

但 User-Agent 可以被任意客户端伪造，仅凭字符串不能确认访问者一定来自百度。对于异常高频、疑似攻击或准备设置访问策略的 IP，应进一步做 DNS 双向验证：

1. 对访问 IP 进行反向 DNS 查询；
2. 检查返回的主机名是否属于百度公开使用的域名范围；
3. 再对该主机名做正向解析；
4. 确认解析结果包含最初的访问 IP。

示例命令：

```bash
host 220.181.xx.xx
host 反向查询得到的主机名
```

不要仅因为 User-Agent 带有 `Baiduspider` 就加入 IP 白名单，也不建议维护一份长期不更新的固定 IP 列表。搜索引擎抓取节点可能调整，验证时应以实际 DNS 结果和百度公开说明为依据。

此外，需要区分百度不同产品的爬虫标识。网页搜索蜘蛛、图片抓取或其他百度服务可能使用不同 User-Agent。分析自然搜索抓取时，应先明确统计范围，避免把所有包含“Baidu”的请求混为一类。

## 按 HTTP 状态码统计抓取结果

如果日志采用常见 combined 格式，状态码通常位于第 9 列，可以使用 `awk` 汇总：

```bash
grep -i 'Baiduspider' access.log |
awk '{count[$9]++} END {
  for (code in count) print code, count[code]
}' | sort
```

可能得到：

```text
200 18642
301 923
304 4107
404 286
500 31
503 74
```

字段位置取决于日志格式。如果统计结果出现 URL、引号或 User-Agent，说明 `$9` 并不是状态码。此时应查看原始行并根据实际分隔方式调整，生产环境也可以使用 GoAccess、ELK、OpenSearch 或日志平台解析结构化字段。

各类状态码可按以下思路判断：

| 状态码 | 日志含义 | 分析重点 |
|---|---|---|
| 200 | 请求成功 | 是否为应抓取的规范页面，内容是否正常输出 |
| 301/308 | 永久重定向 | 是否存在多跳、循环或大量旧 URL |
| 302/307 | 临时重定向 | 是否被长期用于永久迁移，目标是否稳定 |
| 304 | 内容未修改 | 通常与条件请求和缓存验证有关，不等于抓取失败 |
| 403 | 拒绝访问 | 防火墙、WAF、权限或反爬规则是否误拦截 |
| 404/410 | 资源不存在 | 内链、站点地图或历史外链是否仍指向失效 URL |
| 429 | 请求过多 | 限流策略是否影响正常抓取 |
| 500/502/504 | 服务异常 | 程序、网关、上游服务或超时问题 |
| 503 | 暂时不可用 | 维护、过载或主动降载是否持续发生 |

不能只看某个状态码的绝对数量。例如，站点迁移期间出现一批 301 很正常；真正需要关注的是重定向是否一步到达最终 URL，以及旧地址是否仍在内链和 Sitemap 中大量出现。

## 定位产生异常状态码的 URL

总量统计只能说明问题规模，还要继续按 URL 聚合。假设请求路径位于第 7 列，可以统计百度蜘蛛抓取最多的 404 页面：

```bash
grep -i 'Baiduspider' access.log |
awk '$9 == 404 {count[$7]++} END {
  for (url in count) print count[url], url
}' | sort -nr | head -50
```

统计 5xx 页面：

```bash
grep -i 'Baiduspider' access.log |
awk '$9 ~ /^5[0-9][0-9]$/ {print $4, $7, $9}'
```

实际排查时，建议为异常 URL 补充四类信息：

- **首次和最后出现时间**：判断是偶发错误还是持续故障；
- **抓取次数**：区分单次探测与高频重复请求；
- **URL 来源**：检查站内链接、Sitemap、历史改版地址和外部链接；
- **响应耗时**：发现虽然返回 200，但处理时间过长的页面。

404 不应一律重定向到首页。页面确实删除且没有替代内容时，可以保留 404，或明确返回 410；有高度对应的新页面时，再使用 301 指向替代地址。无关重定向可能让用户和搜索引擎难以理解页面迁移关系。

还要警惕“软 404”：服务器返回 200，但页面正文显示“内容不存在”“商品已下架”或只有空模板。仅统计状态码无法发现这类问题，需要抽样请求页面并检查标题、正文长度和模板特征。

## 结合时间维度判断问题严重程度

状态码最好按小时或按天统计，而不是只看一个月总数。时间趋势能够显示发布、迁移、服务器故障或 WAF 规则变更带来的影响。

例如，从 Nginx 日志中统计每天的 5xx 数量时，应根据自己的时间字段格式编写脚本。更稳妥的做法是先将日志导入日志分析系统，然后按以下维度建立图表：

- 百度蜘蛛请求总量；
- 2xx、3xx、4xx、5xx 的数量与占比；
- 404 和 5xx 排名前列的 URL；
- 平均响应时间及高分位响应时间；
- 不同主机名、目录、设备类型或页面模板的异常率。

分析时应对比“异常率”，而不只是数量。抓取量从每天 1 万次增至 10 万次，5xx 从 10 次增至 30 次，数量虽然上升，但比例反而下降。反之，抓取量下降且 5xx 占比快速增加，通常更值得立即排查。

日志轮转也不能忽略。Nginx 常由 `logrotate` 生成 `access.log.1` 或压缩文件，可使用 `zgrep` 检索历史日志：

```bash
zgrep -hi 'Baiduspider' /var/log/nginx/access.log*.gz
```

统计跨天数据时需统一时区，并避免把重复导入的日志计算两次。

## 从日志结论落实修复与复查

完成统计后，可以按影响顺序处理：

1. **优先修复持续性 5xx、超时和连接失败**，同时检查应用错误日志、数据库慢查询及上游服务状态；
2. **检查 403、429 和 503**，确认安全策略或限流是否误伤已验证的百度蜘蛛；
3. **清理重定向链和循环**，让旧 URL 尽量直接到达最终规范地址；
4. **修正站内 404 来源**，更新导航、正文链接、Canonical、Hreflang 和 Sitemap；
5. **处理参数 URL 与重复路径**，从链接生成规则入手，避免持续制造无价值抓取地址；
6. **修复后持续观察日志**，确认异常状态码及对应 URL 的请求趋势是否回落。

日志反映的是百度蜘蛛实际获得的服务器响应，比单纯在浏览器中测试更接近抓取现场，但它不能单独解释索引和排名变化。robots.txt、页面内容、规范化信号、内部链接以及网站质量仍需结合检查。

一套可靠的分析流程应当是：确认日志字段，验证蜘蛛身份，按状态码和 URL 聚合，再结合时间、耗时及页面类型定位原因。修复后保留前后数据进行复查，才能判断服务器返回是否真正恢复稳定，而不是只完成一次性的日志筛选。
