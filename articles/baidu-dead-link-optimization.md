# 百度SEO网站死链检测与处理方法

{% raw %}

## 什么是死链，为什么需要及时处理

死链通常是指已经无法正常访问、服务器返回 `404` 或 `410` 状态码的 URL。常见来源包括文章删除、目录调整、URL 规则变更、域名迁移、文件改名，以及模板中残留的错误链接。

并非所有异常 URL 都属于死链：

- `404 Not Found`：资源不存在，是最常见的死链状态。
- `410 Gone`：资源已永久删除，含义比 404 更明确。
- `301 Moved Permanently`：页面已永久迁移，不属于死链。
- `302 Found`：临时跳转，需要确认是否符合实际需求。
- `500`、`502`、`503`：服务器故障或临时不可用，不能直接当作死链处理。
- 返回 `200` 但页面显示“内容不存在”：属于软 404，会增加搜索引擎判断页面状态的难度。

少量死链通常不会直接造成严重问题，但大量无效 URL 会浪费抓取资源，也会影响用户浏览体验。处理重点不是简单“隐藏链接”，而是让每个失效 URL 返回与实际情况一致的状态。

## 如何全面检测网站死链

仅依靠人工点击很难发现深层页面中的问题，建议结合站点抓取、服务器日志和百度平台数据进行排查。

### 使用爬虫工具扫描站内链接

可以使用 Screaming Frog、Sitebulb、Xenu 等工具抓取网站。扫描完成后，重点筛选：

- 状态码为 404 或 410 的页面；
- 指向失效页面的内部链接来源；
- 多次跳转或循环跳转的 URL；
- 返回 200 但正文为空的页面；
- 图片、CSS、JavaScript 等静态资源死链。

扫描时应从首页和重要栏目页开始，并允许工具跟踪站内链接。大型网站可以分目录抓取，避免一次扫描给服务器造成过大压力。

### 查看百度搜索资源平台

在百度搜索资源平台中，可以关注抓取异常、索引相关数据以及死链提交工具。不同站点权限和平台版本显示的入口可能有所不同，具体以后台现有功能为准。

需要注意，平台发现的异常 URL 只是线索。正式处理前，应再次请求 URL，确认它当前返回的是 404、410、5xx，还是已经恢复正常。

### 分析服务器访问日志

服务器日志能够发现百度蜘蛛实际访问过的失效地址。以 Nginx 日志为例，可初步统计 404 请求：

```bash
awk '$9 == 404 {print $7}' access.log | sort | uniq -c | sort -nr
```

如果还需要筛选百度蜘蛛访问记录，可以先结合 User-Agent 查找：

```bash
grep -i "Baiduspider" access.log | awk '$9 == 404 {print $7}' | sort | uniq -c
```

User-Agent 可以伪造，因此涉及安全判断时还应进行反向 DNS 等验证；但用于普通死链排查时，它可以提供有价值的参考。

### 手动确认 HTTP 状态

对重要 URL 可使用 `curl` 检查响应头：

```bash
curl -I https://www.example.com/old-page
```

重点查看第一行状态码和 `Location` 响应头。若要跟踪完整跳转链，可使用：

```bash
curl -I -L https://www.example.com/old-page
```

## 根据死链类型选择处理方式

检测出死链后，不应全部重定向到首页，而要先判断原页面是否有替代内容。

| 情况 | 推荐处理 |
|---|---|
| 页面被误删，仍有访问价值 | 恢复原 URL，并返回 200 |
| 页面永久迁移，存在高度对应的新页面 | 使用 301 跳转到新页面 |
| 页面彻底删除，没有合适替代内容 | 返回 404 或 410 |
| 站内链接地址写错 | 修改链接，使其指向正确页面 |
| 外部网站链接失效 | 更新、删除链接，或寻找可靠替代来源 |
| 短暂服务器故障 | 修复服务器，不要批量标记为永久死链 |
| URL 仅大小写或斜杠规则不同 | 统一规范，并视情况设置 301 |

301 的目标页面应与旧页面内容具有明确对应关系。例如旧产品页面迁移到同一产品的新地址，可以设置 301；如果产品已经下架且没有替代品，跳转到首页或无关分类页并不合理。

对于由错误参数、异常分页或程序漏洞生成的大量 URL，应先修复产生入口。否则即使提交了旧死链，网站仍可能持续制造新的无效地址。

## 正确配置 404、410 与 301

自定义 404 页面可以提供返回首页、站内搜索和热门栏目入口，但服务器必须保留正确的 `404` 状态，不能因为显示了美观页面就返回 `200`。

Nginx 可参考：

```nginx
error_page 404 /404.html;

location = /404.html {
    internal;
}
```

检查配置后执行：

```bash
nginx -t
```

确认无误再重新加载服务。不要使用 `error_page 404 =200 /404.html;`，因为这会把不存在的页面伪装成正常页面。

对确定迁移的单个地址，可以配置精确 301：

```nginx
location = /old-page.html {
    return 301 https://www.example.com/new-page.html;
}
```

Apache 环境可在支持重写规则的情况下使用：

```apache
Redirect 301 /old-page.html https://www.example.com/new-page.html
ErrorDocument 404 /404.html
```

配置完成后要检查是否出现跳转链，例如旧 URL 先跳到中间地址，再跳到最终页面。能够直接跳转时，应尽量减少不必要的中间环节。

如果网站部署在 GitHub Pages，可以在发布目录创建 `404.html` 作为自定义错误页。GitHub Pages 本身不提供类似 Nginx 的任意服务器级重定向配置；HTML 的刷新跳转也不等同于 HTTP 301。需要严格控制状态码和复杂重定向时，可结合自定义域名、反向代理或 CDN 的规则能力，但应以实际服务商支持的功能为准。

## 向百度提交死链

完成技术处理后，可以整理百度已经收录或抓取过的死链。常见做法是生成一个文本文件，每行放置一个完整 URL，例如：

```text
https://www.example.com/old-a.html
https://www.example.com/old-b.html
https://www.example.com/news/expired.html
```

文件本身应能被公开访问并返回 `200`，文件中列出的 URL 则应稳定返回 `404` 或 `410`。然后在百度搜索资源平台中查找死链提交相关入口，按后台要求提交文件地址。由于平台界面和提交规则可能调整，应以当前页面说明为准。

提交前应注意：

1. 不要提交已经恢复为 200 的页面。
2. 不要提交正在执行 301 的迁移 URL。
3. 不要把 robots.txt 屏蔽当作死链删除手段。
4. 不要混入其他域名或协议错误的地址。
5. URL 数量较多时，应先去重并统一编码格式。
6. 保留死链文件一段时间，方便百度再次抓取确认。

`robots.txt` 只能限制部分抓取行为，不能保证已存在的 URL 从搜索结果中消失。如果先屏蔽抓取，搜索引擎反而可能无法重新访问并确认页面已经返回 404。

## 处理后的验证与长期维护

死链修复不是提交后就结束，还需要持续验证。建议在处理后的数天到数周内重复检查以下内容：

- 旧 URL 是否稳定返回预期状态；
- 301 是否准确到达最终页面；
- 自定义 404 页面是否错误返回 200；
- 页面模板、导航和正文中是否仍指向死链；
- 百度蜘蛛是否还在频繁访问同一批异常地址；
- 网站是否继续生成新的错误参数或无效路径。

可以按周统计服务器 404 日志，并优先处理访问量高、被内部大量引用或曾经获得外部链接的 URL。网站改版前还应导出旧 URL 清单，建立旧地址与新地址的映射表，再分批上线和验证。

有效的死链治理应形成“发现、分类、修复、提交、复查”的闭环。正确状态码、准确的站内链接和稳定的服务器响应，比把所有错误页面跳转到首页更有利于搜索引擎理解网站结构，也能减少用户访问无效页面的情况。
