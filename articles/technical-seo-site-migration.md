# 网站迁移SEO完整操作指南

{% raw %}

网站迁移可能涉及更换域名、切换 HTTPS、调整目录结构、更换 CMS、服务器迁移或整站改版。搜索引擎需要重新确认页面地址、内容关系和站点质量，因此迁移期间常出现抓取异常、收录波动和流量下降。正确的目标不是追求“完全无波动”，而是保留重要页面的信号，并让搜索引擎尽快理解新旧网站之间的对应关系。

## 先判断迁移类型与影响范围

不同迁移方式的 SEO 风险并不相同：

- **仅更换服务器**：URL 不变，主要风险来自 DNS、响应速度、服务器稳定性和配置差异。
- **HTTP 切换到 HTTPS**：协议变化会产生新 URL，需要统一重定向、规范链接和资源地址。
- **更换域名**：影响范围较大，需要逐页重定向，并在搜索平台提交域名变更信息。
- **调整 URL 结构**：例如 `/article/123` 改为 `/blog/topic-name`，重点是建立准确映射。
- **更换 CMS 或整站改版**：除 URL 外，还可能改变标题、正文、内链、结构化数据和渲染方式。
- **合并或拆分网站**：需决定哪些页面保留、合并、删除，以及信号应转移到哪个地址。

不要同时进行过多不必要的改动。例如更换域名时又大规模删除内容、重写标题和调整导航，会增加问题定位难度。如果业务允许，可将服务器迁移、视觉改版和内容清理分阶段完成。

## 迁移前建立数据基线与 URL 清单

上线前应保留可对比的数据，否则迁移后很难判断流量变化来自季节性波动、排名变化还是技术故障。

建议记录以下指标：

- 自然搜索流量、转化量及主要落地页；
- 已收录页面数量和有效索引状态；
- 核心关键词及对应排名页面；
- 页面响应状态、规范链接和可索引性；
- 外链较多、流量较高或承担转化的重点页面；
- XML Sitemap、robots.txt、结构化数据和站内链接情况；
- 当前服务器日志及最近一次完整备份。

URL 清单不能只依赖 Sitemap。还应结合网站爬取结果、分析工具落地页、搜索平台数据、服务器日志和 CMS 数据库，找出孤立页面及历史地址。

随后为每个旧 URL 指定处理方式：

| 旧页面情况 | 推荐处理 |
|---|---|
| 新站存在相同内容 | 301 到对应新 URL |
| 多个旧页面被合并 | 301 到相关性最高的合并页面 |
| 页面被替代 | 301 到真正满足原需求的新页面 |
| 永久删除且没有替代内容 | 返回 404 或 410 |
| 暂时不可用 | 保留原地址或谨慎使用 302 |

不要把所有旧页面统一跳转到首页。这种做法缺乏内容对应关系，用户体验较差，搜索引擎也可能将其视为软 404。

## 设计并测试 301 重定向

永久迁移通常使用服务端 **301 重定向**。映射应尽量做到一对一，并保留必要的路径和查询参数。

如果只是更换域名且路径完全一致，Nginx 可采用类似配置：

```nginx
server {
    listen 80;
    server_name old.example.com www.old.example.com;

    return 301 https://new.example.com$request_uri;
}
```

实际部署时还要处理旧域名的 HTTPS 请求，因此旧证书不应在迁移后立即撤销。否则用户访问旧的 HTTPS 地址时，会在收到重定向前遇到证书错误。

检查重定向时应关注：

1. 旧 URL 是否直接到达最终新地址；
2. 是否出现 `301 → 301 → 200` 的跳转链；
3. HTTP、HTTPS、带 `www` 和不带 `www` 的版本是否统一；
4. 大小写、尾部斜杠和参数是否产生重复页面；
5. 重定向目标是否返回 200，而不是 404 或 5xx；
6. 移动端、不同语言版本是否跳转到正确页面。

应避免循环跳转和多层跳转。旧地址最好直接指向最终规范 URL，而不是先跳到新域名，再跳到 HTTPS，最后又调整尾部斜杠。

301 规则需要长期保留。过早删除可能导致仍存在于外链、收藏夹或搜索结果中的旧地址失效。

## 同步更新站内 SEO 与技术配置

仅配置重定向还不够，新站自身也要明确使用新 URL。

上线前后逐项检查：

- 页面标题、正文和关键功能是否完整迁移；
- `rel="canonical"` 是否指向新站可索引的规范地址；
- 导航、正文链接、面包屑、分页和 hreflang 是否使用新 URL；
- 图片、CSS、JavaScript、字体及接口资源是否正常加载；
- robots.txt 是否误用了测试环境的禁止抓取规则；
- 页面是否残留 `noindex`；
- XML Sitemap 是否只包含返回 200 的新规范 URL；
- 结构化数据中的 URL、图片和组织信息是否同步更新；
- Open Graph、分享链接和 RSS 地址是否仍引用旧域名；
- 服务器是否能稳定返回正确的 200、301、404 和 410 状态码。

测试环境通常会通过登录验证、IP 白名单或 `noindex` 防止被收录。正式上线时必须移除这些限制，但不要为了“方便抓取”而允许搜索引擎访问未完成的测试站。

如果迁移涉及 JavaScript 框架，还应确认重要正文和链接能够被搜索引擎渲染。服务端渲染或预渲染并非所有网站都必须采用，但核心内容不应依赖用户操作后才出现。

## 制定上线顺序并控制切换风险

选择业务低峰期上线，并提前准备回滚方案。若更换服务器或域名，可提前降低 DNS 的 TTL，以缩短切换期间的缓存时间；但 TTL 只影响 DNS 更新速度，不能解决错误配置。

推荐上线顺序如下：

1. 冻结内容发布，避免迁移过程中数据不一致；
2. 完成数据库、文件和配置备份；
3. 在受控环境中爬取新站并修复问题；
4. 部署新站、证书和重定向规则；
5. 更新 DNS，并验证不同网络下的解析结果；
6. 检查核心页面、表单、登录、支付和统计代码；
7. 发布新的 robots.txt 与 XML Sitemap；
8. 恢复内容更新并持续监控服务器。

正式切换后应立即抽查首页、栏目页、重点落地页、长尾页面和历史 URL。不要只测试浏览器能否打开页面，还应使用状态码检测工具确认实际响应。

若是更换域名，可在 Google Search Console 中验证新旧域名，并在符合条件时使用“地址更改”工具；同时提交新 Sitemap。其他搜索平台应按照各自提供的站点验证、改版或链接提交机制操作。提交工具能帮助搜索引擎发现变化，但不代表页面一定收录或排名保持不变。

## 上线后监控与处理异常

迁移后的前几天应高频检查，随后持续观察数周。重点指标包括：

- 旧 URL 的抓取量是否下降，新 URL 是否开始被抓取；
- 404、软 404、5xx 和重定向错误是否增加；
- Sitemap 中页面的发现、抓取和索引状态；
- 自然搜索流量是否集中下降在某个目录或设备；
- 重点页面是否被错误规范到其他地址；
- 服务器响应时间、CPU、带宽和日志中的爬虫行为；
- 统计工具是否因代码遗漏、跨域配置错误而少记流量。

如果流量明显下降，可按以下顺序排查：

1. 确认分析代码和报表口径没有变化；
2. 检查页面是否可访问、可抓取且没有 `noindex`；
3. 检查 robots.txt、canonical 和重定向目标；
4. 对比迁移前后的标题、正文、内链和页面模板；
5. 查看服务器日志是否存在大量 404、5xx 或抓取阻断；
6. 按目录、页面类型、国家和设备定位下降范围。

不要因为短期波动频繁撤销域名或 URL。反复切换会制造新的重定向和索引信号。只有出现严重故障，例如核心页面大面积返回 5xx、数据库缺失或新站无法使用时，才应依据预先制定的回滚方案处理。

一次可控的迁移依赖准确的 URL 映射、直接的永久重定向、完整的站内配置和持续监测。把高价值页面与用户访问路径放在优先位置，并保留旧站信号和必要备份，通常比上线后再集中修补更稳妥。
