# Sitemap提升百度URL发现效率的方法

{% raw %}

Sitemap 的主要作用是向搜索引擎提供一份可抓取 URL 清单，尤其适合新站、页面较深、更新频繁或内部链接尚不完善的网站。它能降低百度发现页面的成本，但提交 Sitemap 不等于页面一定被抓取、收录或获得更高排名。要真正提升 URL 发现效率，关键在于文件内容准确、更新及时，并保证其中的地址可以正常访问。

## 先确认哪些 URL 应该进入 Sitemap

不要把网站生成的所有地址不加区分地写入 Sitemap。优先提交希望参与搜索、内容完整且状态稳定的规范 URL，例如：

- 文章、产品、栏目等主要内容页；
- HTTP 状态码为 `200` 的页面；
- 未被 `robots.txt` 阻止抓取的地址；
- 没有设置 `noindex` 的页面；
- 页面 canonical 指向自身，或至少不存在规范化冲突；
- 无需登录、验证码或特殊 Cookie 即可访问。

以下地址通常不应放入 Sitemap：

- 失效页面、软 404 页面；
- 301、302 跳转地址；
- 搜索结果页、筛选参数页和重复分页组合；
- 测试环境、后台管理和会员中心页面；
- canonical 指向其他页面的重复 URL；
- 被明确禁止索引的页面。

如果 Sitemap 中存在大量重定向、重复页或错误页，百度需要额外处理这些无效地址，也会降低这份 URL 清单的可信度和使用效率。

## 按规范生成 XML Sitemap

常见的 XML Sitemap 基本结构如下：

```xml
<?xml version="1.0" encoding="UTF-8"?>
<urlset xmlns="http://www.sitemaps.org/schemas/sitemap/0.9">
  <url>
    <loc>https://www.example.com/article/a.html</loc>
    <lastmod>2025-03-01</lastmod>
  </url>
  <url>
    <loc>https://www.example.com/article/b.html</loc>
    <lastmod>2025-03-05T10:30:00+08:00</lastmod>
  </url>
</urlset>
```

其中，`loc` 是必需字段，应填写完整的绝对地址，并保持协议、主机名和路径形式统一。网站已经全面使用 HTTPS 时，不要继续提交 HTTP 版本；网站确定使用带 `www` 的主域名时，也不要混入不带 `www` 的重复地址。

`lastmod` 表示页面内容最后一次发生实质变化的时间。文章正文修改、产品信息更新或页面数据明显变化时可以更新该字段，仅因模板渲染、访问次数变化而每天改写日期没有实际意义。错误的更新时间可能让搜索引擎难以判断哪些页面值得重新抓取。

`changefreq` 和 `priority` 属于可选字段，搜索引擎不一定按站长填写的值安排抓取。与其给全部页面设置最高优先级，不如维护准确的 URL 和 `lastmod`。

单个 Sitemap 按通用协议最多包含 50,000 个 URL，未压缩文件大小不超过 50MB。实际运营中可以设置更小的拆分阈值，避免文件生成、下载或检查过慢。

## 拆分文件并突出新增内容

内容规模较大时，可按页面类型或更新时间拆分，例如：

```text
/sitemap-posts.xml
/sitemap-products.xml
/sitemap-categories.xml
/sitemap-2025-03.xml
```

再通过 Sitemap 索引统一管理：

```xml
<?xml version="1.0" encoding="UTF-8"?>
<sitemapindex xmlns="http://www.sitemaps.org/schemas/sitemap/0.9">
  <sitemap>
    <loc>https://www.example.com/sitemap-posts.xml</loc>
    <lastmod>2025-03-08</lastmod>
  </sitemap>
  <sitemap>
    <loc>https://www.example.com/sitemap-products.xml</loc>
    <lastmod>2025-03-08</lastmod>
  </sitemap>
</sitemapindex>
```

拆分的价值不仅是避免超限，也便于定位问题。例如，产品 Sitemap 报错时，不会影响文章文件的维护；结合服务器日志，还能判断百度蜘蛛主要访问了哪一类 URL。

对于更新频繁的网站，可以保留一份覆盖全部有效页面的 Sitemap，同时单独生成近期新增或更新页面清单。新增内容发布后应尽快进入文件，删除、合并或跳转的页面则应及时移除。需要注意，Sitemap 不是历史档案，没有必要永久保留已经失效的地址。

## 让百度能够稳定获取文件

Sitemap 本身必须可以被百度直接访问。发布后至少检查以下项目：

1. 文件返回 `200 OK`，而不是跳转、403 或 5xx；
2. XML 编码正确，特殊字符已经转义；
3. 文件地址在公网环境下无需登录即可打开；
4. CDN、防火墙和安全插件没有拦截正常搜索引擎抓取；
5. Sitemap 中的 URL 属于当前验证的网站范围；
6. 文件更新后，缓存能够在合理时间内刷新。

可以在 `robots.txt` 中声明 Sitemap 地址：

```text
User-agent: *
Disallow:

Sitemap: https://www.example.com/sitemap.xml
```

`Sitemap` 声明通常放在文件末尾，地址使用绝对 URL。它能帮助访问 `robots.txt` 的搜索引擎找到 Sitemap，但不能替代平台提交，也不会覆盖抓取限制。如果某个页面被 `robots.txt` 禁止抓取，即使它出现在 Sitemap 中，百度也可能无法读取页面内容。

在服务器端还应避免为百度蜘蛛设置激进的频率限制。如果 Sitemap 经常返回 429、连接超时或大小异常，URL 发现速度会受到影响。

## 在百度搜索资源平台提交并维护

网站完成验证后，可登录百度搜索资源平台，在链接提交相关功能中查看当前站点可用的提交方式，并提交 Sitemap 文件地址。平台的具体入口、配额和功能可能随站点权限或产品调整而变化，应以后台实际显示为准。

提交时建议遵循以下顺序：

1. 先验证提交的站点协议和域名是否正确；
2. 用浏览器或命令行确认 Sitemap 可访问；
3. 检查 XML 语法及抽样 URL 状态；
4. 在资源平台添加 Sitemap 地址；
5. 观察文件读取状态、错误提示及后续抓取情况；
6. 修复问题后更新原文件，不要频繁创建内容完全相同的新地址。

对于少量新发布的重要页面，可以根据后台提供的普通提交、API 提交等方式补充推送。API 适合在内容发布流程中自动提交新增 URL，但应遵守平台给出的接口格式和配额。Sitemap 更适合提供稳定、完整的 URL 集合，两者可以配合使用，而不是互相替代。

## 用数据判断 URL 是否真正被发现

“文件提交成功”只说明百度能够接收或读取 Sitemap，并不代表其中每个页面已经进入索引。后续应结合三类信息检查效果。

### 搜索资源平台反馈

关注 Sitemap 的读取状态、发现数量和错误信息。如果提交数量与有效 URL 数量差距很大，应检查 XML 格式、文件缓存、域名混用和页面状态。

### 服务器访问日志

在日志中筛选百度蜘蛛对 Sitemap 及页面 URL 的访问记录，观察：

- Sitemap 是否被定期请求；
- 新 URL 在发布后多久出现首次抓取；
- 是否存在大量 404、301、403 或 5xx；
- 抓取是否集中在参数页，而重要内容页反而很少访问。

仅凭 User-Agent 不能完全确认请求身份；需要严格识别时，可结合 IP 反向解析及正向验证，避免把伪装请求当成真实百度蜘蛛。

### 站内技术质量

如果 URL 已被发现但长期不抓取或不进入索引，问题往往不只在 Sitemap。还应检查页面内容是否重复、内部链接是否可达、服务器是否稳定、移动端展示是否正常，以及 canonical、`noindex` 和 robots 规则是否相互冲突。

高质量的 Sitemap 应当是一份持续维护的有效页面清单。先清理无效 URL，再准确记录更新时间，通过百度搜索资源平台和 `robots.txt` 提供入口，最后用日志验证实际抓取，才能稳定降低百度发现新增及更新页面的成本。
