# JavaScript网站搜索引擎抓取优化指南

{% raw %}

## 先判断网站是否真的存在抓取问题

JavaScript 网站并非天然不利于 SEO。问题通常在于：服务器返回的初始 HTML 内容过少，核心信息必须等脚本执行后才出现，而不同搜索引擎执行 JavaScript 的能力、资源限制和等待时间并不一致。

搜索引擎处理页面大致包含三个环节：

1. **抓取**：请求 URL，读取服务器响应及其中的链接。
2. **渲染**：执行可用的 JavaScript，生成最终 DOM。
3. **索引**：理解正文、标题、规范网址等信息，决定是否纳入索引。

即使搜索引擎能够渲染 JavaScript，也不代表每次抓取都会立即完成渲染。脚本报错、接口超时、资源被阻止或内容必须交互后才加载，都可能导致搜索引擎看到不完整的页面。

可以先做一个简单检查：

```bash
curl -L https://example.com/product/123
```

查看返回的 HTML 中是否已经包含页面标题、主要正文、产品名称或文章内容。如果只有一个空容器：

```html
<div id="app"></div>
<script src="/assets/app.js"></script>
```

说明核心内容完全依赖客户端渲染，应进一步评估是否需要服务端渲染或静态生成。

## 优先选择可输出完整 HTML 的渲染方案

常见 JavaScript 网站主要有以下几种渲染方式。

### 客户端渲染（CSR）

浏览器先获得基础 HTML，再通过 JavaScript 请求数据并构建页面。它适合登录后台、管理工具等不依赖自然搜索流量的页面，但公开文章、商品详情和落地页不宜只向爬虫提供空壳 HTML。

### 服务端渲染（SSR）

服务器根据请求生成包含正文的 HTML，浏览器随后完成 hydration，使页面具备交互能力。SSR 适合内容变化频繁、需要根据请求实时生成的页面，但要关注服务器响应时间、缓存以及渲染失败处理。

### 静态站点生成（SSG）

在构建阶段生成每个公开 URL 的 HTML 文件，适合文档、博客、帮助中心和更新频率较低的产品页面。静态页面通常更容易被抓取，也便于部署到 CDN。

实际项目可以混合使用：内容页采用 SSG 或 SSR，用户中心继续使用 CSR。Next.js、Nuxt、SvelteKit 等框架都提供相应能力，但使用框架本身并不等于完成优化，最终仍要检查真实响应中的 HTML。

如果采用“动态渲染”，即向爬虫和普通用户返回不同渲染结果，应确保两者主体内容一致。长期维护两套输出容易产生差异，因此它通常更适合作为旧系统的过渡方案，而不是首选架构。

## 让每个页面拥有可抓取的 URL 和链接

搜索引擎主要通过普通链接发现页面。站内导航应尽量输出带 `href` 的 `<a>` 元素：

```html
<a href="/guides/javascript-seo">JavaScript SEO 指南</a>
```

不要只依赖点击事件：

```html
<div onclick="goToGuide()">查看指南</div>
```

后者对键盘访问、可访问性和链接发现都不友好。即使前端路由会拦截链接点击，HTML 中仍应保留有效的目标地址。

路由配置还要注意以下问题：

- 为每个可索引页面提供唯一、稳定的 URL。
- 不要使用 `#/article/123` 作为主要内容路由。井号后的片段通常不会作为独立服务器资源请求。
- 参数排序、大小写和尾斜杠规则应保持一致。
- 使用 History API 路由时，服务器需要把有效的深层路径返回给应用，而不是直接响应 404。
- 已删除或不存在的内容应返回真实的 `404` 或 `410` 状态码，不要全部重定向到首页。
- 永久迁移页面使用服务端 `301` 或 `308`，不要只在脚本中执行跳转。

GitHub Pages 可以托管构建后的静态文件，但不提供通用的服务器端重写规则。纯 SPA 的深层地址可能直接返回 GitHub Pages 的 404 页面。面向搜索的项目更适合在构建时为各路由生成对应 HTML 文件；利用自定义 `404.html` 转回 SPA 只能缓解访问问题，不能等同于正常的 HTTP 路由和状态码处理。

## 在初始 HTML 中提供关键 SEO 信息

页面的主要文本、标题和描述最好随 HTML 一起返回，而不是等接口请求完成后再插入。每个可索引页面至少应检查：

```html
<title>具体页面标题</title>
<meta name="description" content="对本页内容的独立概述">
<link rel="canonical" href="https://example.com/guides/javascript-seo">
<meta name="robots" content="index,follow">
```

需要避免以下常见错误：

- 所有路由共用同一个 `title` 和 description。
- 先输出错误的 canonical，再依靠 JavaScript 修改。
- 在初始 HTML 中设置 `noindex`，渲染后才移除。
- 页面正文已经改变，但结构化数据仍保留旧价格、旧日期或旧作者。
- 无限滚动内容没有可单独访问的分页 URL。

结构化数据可以采用 JSON-LD，但其中描述的对象必须与用户可见内容一致。添加结构化数据只是帮助搜索引擎理解页面，不代表一定会出现富媒体搜索结果。

对于多语言网站，还应让每种语言拥有独立 URL，并正确输出互相对应的 `hreflang`。不要仅根据浏览器语言在同一 URL 中替换全部正文，否则搜索引擎可能难以稳定发现不同语言版本。

## 保证脚本、接口和延迟内容可正常渲染

爬虫需要获取渲染所需的 JavaScript、CSS、字体或公开数据接口。不要在 `robots.txt` 中误封关键资源目录，例如：

```txt
User-agent: *
Disallow: /admin/
Disallow: /account/
```

如果 `/assets/` 中包含页面渲染必需的脚本，就不应仅为了“节省抓取”而屏蔽它。还要检查 CDN、防火墙和反爬规则，避免把正常搜索引擎请求错误地拦截为 403 或验证码页面。

依赖接口加载内容时，应处理超时和失败状态。公开正文不应要求登录、Cookie 授权、地理位置许可或用户点击后才能出现。懒加载图片可以保留，但应提供真实的图片 URL、尺寸和替代文本：

```html
<img
  src="/images/rendering-guide.webp"
  width="960"
  height="540"
  loading="lazy"
  alt="服务端渲染与客户端渲染流程对比">
```

首屏核心内容不宜在长时间定时器、滚动事件或复杂动画结束后才插入。减少大型脚本、拆分非必要代码、使用缓存和 CDN，既能改善用户体验，也能降低渲染失败的概率。性能优化不会自动带来排名提升，但缓慢或不稳定的页面会增加抓取与使用成本。

## 提交发现信号并持续验证

XML Sitemap 用于帮助搜索引擎发现规范 URL，应只列出希望被索引且返回成功状态的页面：

```xml
<url>
  <loc>https://example.com/guides/javascript-seo</loc>
  <lastmod>2025-03-01</lastmod>
</url>
```

`lastmod` 应反映页面的重要更新，不要在每次构建时无差别修改。Sitemap 不能替代站内链接，也不能绕过 `noindex`、404 或内容质量判断。

上线后可按以下顺序验证：

1. 用 `curl` 查看原始 HTML 和 HTTP 状态码。
2. 在浏览器禁用 JavaScript，确认主要内容是否仍可读取。
3. 检查控制台错误、失败的接口请求及被阻止的资源。
4. 使用 Google Search Console 的网址检查工具查看已抓取页面和渲染结果。
5. 使用对应搜索引擎站长平台监控抓取、索引和 Sitemap 状态。
6. 分析服务器日志，确认爬虫访问了哪些 URL，以及是否频繁遇到 404、重定向链或 5xx。
7. 抽查 canonical、robots、结构化数据和移动端页面是否一致。

优化的核心不是为爬虫制作特殊页面，而是让服务器稳定返回有意义的 HTML、有效链接和准确状态码，并确保渲染后的内容与初始信号一致。完成配置后仍需结合抓取日志和站长平台持续观察，因为可抓取并不等于一定收录，收录也不意味着必然获得更高排名。
