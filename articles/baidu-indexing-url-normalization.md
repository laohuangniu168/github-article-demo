# 百度SEO URL规范化与收录优化指南

{% raw %}

## 为什么要做 URL 规范化

同一内容经常可以通过多个地址访问，例如：

```text
http://example.com/product/1
https://example.com/product/1
https://www.example.com/product/1
https://example.com/product/1/
https://example.com/product/1?from=nav
```

如果这些地址均返回相同或高度相似的正文，搜索引擎需要自行判断哪个才是主要版本。其潜在影响包括：

- 抓取资源被重复地址消耗；
- 页面信号分散到不同 URL；
- 搜索结果中出现非预期地址；
- 收录数量看似增加，但有效页面占比下降；
- 站点改版后，新旧 URL 长期并存。

URL 规范化的目标不是让网址“看起来更短”，而是为每份内容确定唯一、稳定、可抓取的标准地址，并让重定向、页面声明、站内链接和 Sitemap 共同指向它。

## 先确定全站唯一 URL 规则

实施前应形成明确规则，避免开发、运营和模板各自生成不同版本。

### 统一协议与主机名

正式站点通常统一使用 HTTPS，并在带 `www` 与不带 `www` 的域名之间选择一个主版本。没有必要仅为了 SEO 强行选择其中某种形式，关键是保持一致，并将另一版本永久重定向至主域名。

例如确定：

```text
https://www.example.com/
```

那么以下地址应跳转到它：

```text
http://example.com/
http://www.example.com/
https://example.com/
```

### 统一路径格式

需要提前约定：

- URL 是否保留结尾斜杠；
- 英文字母是否统一小写；
- 默认首页文件是否隐藏，如 `index.html`；
- 分类、文章和产品路径是否使用固定结构；
- 中文路径是否保留，还是使用拼音或稳定编号。

Linux 服务器可能区分路径大小写，因此 `/News/` 与 `/news/` 不一定是同一资源。不要只在模板中改链接，还要在服务器端处理旧格式。

### 控制查询参数

追踪参数、排序参数和筛选参数容易生成大量组合：

```text
/article/123?utm_source=xx
/list?sort=price
/list?color=red&page=2
```

对于不改变核心内容的统计参数，应尽量在前端链接中移除，并让其对应到无参数的标准 URL。真正改变内容的筛选页则需单独判断：有稳定搜索需求、内容充足的页面可以保留；组合过多或内容薄弱的页面不宜全部开放抓取。

## 用 301 重定向合并重复地址

当旧 URL 已停用，或多个地址必须合并为一个地址时，服务端 301 永久重定向通常是最清晰的处理方式。它不仅告诉用户资源已迁移，也向搜索引擎传递新旧地址关系。

Nginx 的简化示例如下：

```nginx
server {
    listen 80;
    server_name example.com www.example.com;
    return 301 https://www.example.com$request_uri;
}

server {
    listen 443 ssl;
    server_name example.com;
    return 301 https://www.example.com$request_uri;
}
```

若要移除默认首页文件：

```nginx
location = /index.html {
    return 301 https://www.example.com/;
}
```

实际配置前应检查现有路由、反向代理和 CDN 规则，不能直接照搬示例。尤其要避免：

- 多次跳转：A 跳到 B，B 再跳到 C；
- 重定向循环；
- 所有旧页面都跳到首页；
- 已删除且无替代内容的页面被错误重定向；
- 跳转后丢失有意义的路径或分页信息。

理想状态是旧地址一次跳转到内容最对应的新地址。对于确实永久删除、又没有替代内容的页面，应返回合理的 `404` 或 `410`，而不是制造“软 404”。

## 正确使用 canonical 与页面信号

对于因技术原因无法重定向的重复页面，可以在 HTML 的 `<head>` 中声明规范地址：

```html
<link rel="canonical" href="https://www.example.com/article/123" />
```

canonical 应使用完整绝对 URL，并满足以下条件：

1. 指向返回 `200` 状态码的可访问页面；
2. 目标页面内容与当前页面相同或高度对应；
3. 不指向被 `robots.txt` 阻止、登录限制或已删除的地址；
4. 不在不同页面上机械地全部指向首页；
5. 分页页面不要无条件全部指向第一页，除非第一页确实完整承载全部内容。

需要注意，canonical 通常属于规范化提示，而不是强制命令。搜索引擎会结合重定向、内容相似度、站内链接和 Sitemap 等信息综合判断。因此不能一边声明 A 为规范页，一边在导航、面包屑和相关推荐中持续链接到 B。

每个可索引页面也可以自指 canonical，例如：

```html
<link rel="canonical" href="https://www.example.com/category/page-2" />
```

自指声明有助于明确当前页面的标准形式，但不能替代服务器重定向。对于协议、域名或永久路径迁移，优先使用 301，再配合 canonical 和链接更新。

`robots.txt` 也不适合用来解决规范化问题。先禁止百度抓取重复 URL，可能导致搜索引擎无法看到页面上的 canonical 或重定向关系。若目标是合并地址，应先让必要的抓取发生，再根据参数类型谨慎控制抓取范围。

## 用站内链接、Sitemap 和提交工具统一入口

规范 URL 确定后，站内所有入口都应直接链接到最终地址，包括：

- 主导航、页脚和面包屑；
- 文章列表、相关推荐和产品推荐；
- 图片、移动端模块及结构化数据中的 URL；
- hreflang 等其他页面级声明（如站点确有多语言版本）；
- XML Sitemap。

Sitemap 中只应放置希望百度收录的规范 URL。不要同时提交 HTTP 与 HTTPS、带参数与无参数、旧路径与新路径，也不要放入重定向、404、`noindex` 或需要登录的页面。

示例：

```xml
<url>
  <loc>https://www.example.com/article/123</loc>
  <lastmod>2025-02-18</lastmod>
</url>
```

`lastmod` 应反映内容的真实更新时间，不宜每天批量伪造变化。Sitemap 的作用是帮助发现 URL，并不代表其中页面一定会被收录。

站点可在百度搜索资源平台完成验证，并使用当前控制台提供的 Sitemap 或 URL 提交能力。产品入口和提交额度可能调整，应以平台现行说明为准。新页面、重要更新页或改版后的映射地址可以优先提交，但持续提供原创、完整、可访问的内容仍是基础。

## 收录异常的检查与改版流程

不能只依赖 `site:` 查询判断收录情况，因为它更适合做趋势观察，不一定完整、实时。排查时应结合百度搜索资源平台反馈、服务器日志和页面实际响应。

可以按以下顺序检查：

1. **确认状态码**：规范页返回 `200`，旧页按预期返回 `301`，不存在的页面返回 `404` 或 `410`。
2. **检查跳转链**：使用浏览器开发者工具或 `curl -I` 查看是否存在多跳和循环。
3. **核对可抓取性**：确认没有被 `robots.txt` 误拦截，页面也没有意外添加 `noindex`。
4. **比较页面信号**：canonical、Sitemap、站内链接、结构化数据中的 URL 是否一致。
5. **查看日志**：观察百度蜘蛛是否访问规范页，是否仍大量抓取无效参数和旧路径。
6. **评估内容质量**：规范化只能合并重复信号，无法让空页面、采集页或低价值筛选页自然获得收录。
7. **持续观察**：URL 迁移后的识别与替换需要时间，不宜频繁更换规则或反复撤销重定向。

大型改版时，应先建立逐条映射表，再上线 301，并同步更新模板链接、canonical 和 Sitemap。旧域名或旧路径的重定向应保留足够长时间，同时监控流量、抓取量、404 数量及重要页面的索引变化。

URL 收录优化的核心是“一份内容，一个稳定地址，多种信号保持一致”。先从协议、域名、路径和参数层面确定规则，再通过 301、canonical、站内链接和 Sitemap 落实，最后用状态码、日志及百度平台数据持续验证。它不能保证页面被收录或提升排名，但能减少技术冲突，让搜索引擎更准确地理解站点结构。
